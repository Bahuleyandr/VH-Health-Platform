## Finding 1 — `doctors.search_vector` (real schema gap)

**Classification:** Real schema gap — column missing from `schema.prisma`

**Severity:** Medium

### What the scanner found

```
SELECT .search_vector  —  apps/backend/src/utils/search/searchService.js:78
```

`searchService.js` references `d.search_vector` in two raw-SQL call sites
(`ts_rank(d.search_vector, …)` at line 81 and `d.search_vector @@ …` at line 87).
The alias `d` maps to the `doctors` table via `FROM doctors d`. The `doctors`
model in `prisma/schema.prisma` (lines 4414–4440) has **no `search_vector`
column**.

### Root cause

`search_vector` is a PostgreSQL `tsvector` generated/trigger-maintained column
used for full-text doctor search. Prisma cannot represent `tsvector` natively
so `prisma db pull` silently drops it from the schema model. The column likely
exists in the real database but is invisible to the Prisma schema and therefore
to this scanner.

### Impact

- If the column is missing from the DB (e.g. on a fresh QA DB bootstrapped only
  from `schema.prisma`), every `searchDoctors()` call that reaches the FTS
  branch will fail with `column d.search_vector does not exist`.
- The fallback ILIKE branch at `searchService.js:94` will still work.

### Recommended fix

Add the column (or confirm its presence) in the raw SQL migration baseline and
document it in `prisma/SCHEMA_NOTES.md` as a non-Prisma-representable column:

```sql
-- In the appropriate migration or in 000_baseline.sql comments:
ALTER TABLE doctors
  ADD COLUMN IF NOT EXISTS search_vector tsvector
    GENERATED ALWAYS AS (
      to_tsvector('english', coalesce(name,'') || ' ' || coalesce(specialty,''))
    ) STORED;

CREATE INDEX IF NOT EXISTS idx_doctors_search_vector
  ON doctors USING GIN (search_vector);
```

Add a note in `prisma/SCHEMA_NOTES.md`:
> `doctors.search_vector` — tsvector generated column for FTS; omitted from
> Prisma model by design (Prisma doesn't support tsvector). Maintained by the
> SQL migration baseline.

## Finding 2 — `radiology_orders.patient_uid__INTERP__` (false positive)

**Classification:** Scanner false positive — not a real drift issue

**Severity:** None (scanner limitation)

### What the scanner found

```
SELECT .patient_uid__INTERP__  —  apps/backend/src/services/radiology/pacsService.js:198
```

### Root cause

The scanner's `stripInlineDollarInterp()` replaces every `${…}` template
expression with the literal string `__INTERP__`. At line 207 of `pacsService.js`
the SQL template literal contains:

```javascript
`LEFT JOIN users u ON u.uid = ro.patient_uid${userTenantJoin}`
```

`${userTenantJoin}` is a conditional tenant-filter fragment (either `""` or
`" AND u.tenant_id = $N::uuid"`). After substitution the scanner sees
`ro.patient_uid__INTERP__` and treats this as a single column name on the
`radiology_orders` table.

The actual column referenced is `patient_uid`, which **is present** in
`schema.prisma` (line 7855: `patient_uid String @db.Uuid`).

### Impact

None — this is a scanner bug, not production drift.

### Recommended fix

The scanner should detect when `__INTERP__` immediately trails a valid column
name without a word boundary (space, comma, parenthesis) and suppress the
finding. A minimal guard in `analyseSelectRefs()` after the `refRe` match:

```js
// Skip if the column name ends with the interpolation placeholder —
// the placeholder is part of a JOIN/WHERE fragment, not the column name.
if (col.endsWith('__INTERP__')) continue;
```

Alternatively, restructure the SQL at `pacsService.js:207` so the template
variable is not concatenated directly to a column name:

```javascript
// Before
`LEFT JOIN users u ON u.uid = ro.patient_uid${userTenantJoin}`

// After
`LEFT JOIN users u ON u.uid = ro.patient_uid
       ${userTenantJoin}`
```

(A leading newline + spaces keeps the expression separate; the scanner only
substitutes `${…}`, so `ro.patient_uid\n` is safe.)

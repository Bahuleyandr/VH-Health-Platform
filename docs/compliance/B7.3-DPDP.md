**Framework:** Digital Personal Data Protection Act, 2023 (India) and DPDP Rules, 2025  
**Milestone:** WS7 B7.3 — DPDP audit artifacts (S-Tier Roadmap 2026-06-13)

- DPDP Act 2023: MeitY, gazetted 11-Aug-2023

## 1. Requirement Catalogue

### 1.1 Data Fiduciary Obligations (DPDP Act Chapter II)

| Req ID | Obligation | Act Section |
|---|---|---|
| DPDP-DF-01 | Process personal data only for lawful purpose with notice and consent, or for specified legitimate uses | §4, §6, §7 |
| DPDP-DF-02 | Give Data Principal a clear notice of personal data being collected, purpose, and rights | §5 |
| DPDP-DF-03 | Consent must be free, specific, informed, unconditional, and unambiguous | §6(1) |
| DPDP-DF-04 | Consent request must not be bundled with other purposes (no bundled/omnibus consent) | §6(2) |
| DPDP-DF-05 | Consent withdrawal must be as easy as giving consent | §6(4) |
| DPDP-DF-06 | Legitimate uses without consent: medical emergency, state benefit delivery, employment-related | §7 |
| DPDP-DF-07 | Data minimisation: collect only data necessary for stated purpose | §8(1) |
| DPDP-DF-08 | Purpose limitation: data used only for the purpose for which consent was given | §8(2) |
| DPDP-DF-09 | Storage limitation: data not retained beyond the period necessary for the purpose | §8(7) |
| DPDP-DF-10 | Implement appropriate technical and organisational measures to ensure security | §8(5) |
| DPDP-DF-11 | Notify Data Protection Board and affected Data Principals of a personal data breach | §8(6), §64(1) |

### 1.2 Data Principal Rights (DPDP Act Chapter III)

| Req ID | Right | Act Section |
|---|---|---|
| DPDP-DP-01 | Right to access: summary of personal data processed and processing activities | §11 |
| DPDP-DP-02 | Right to correction and erasure: correct inaccurate, update incomplete data; erase if no longer needed | §12 |
| DPDP-DP-03 | Right to grievance redressal: response within timeline set in Rules | §13 |
| DPDP-DP-04 | Right to nominate: nominate another person to exercise rights in case of death/incapacity | §14 |
| DPDP-DP-05 | Children's data: additional consent requirements for children (< 18); no tracking or behavioural monitoring | §9 |
| DPDP-DP-06 | Right to withdraw consent: effect on further processing; no withdrawal to be penalised | §6(4) |

### 1.3 Data Fiduciary Duties — Processors and Cross-Border

| Req ID | Obligation | Act Section |
|---|---|---|
| DPDP-PR-01 | Data processor must process data only per Data Fiduciary instructions; data processing agreement (DPA) required | §8(3), §21 |
| DPDP-PR-02 | Sub-processors bound by same obligations | §8(3) |
| DPDP-CB-01 | Cross-border transfers: personal data may be transferred to countries/territories notified by Central Government; counsel must confirm | §16 |

### 1.4 Significant Data Fiduciary (SDF) — If notified

| Req ID | Obligation | Act Section |
|---|---|---|
| DPDP-SDF-01 | Data Protection Impact Assessment (DPIA) | §29 |
| DPDP-SDF-02 | Periodic audit by independent data auditor | §29(2)(b) |
| DPDP-SDF-03 | Appointment of Data Protection Officer (DPO) | §30 |

### 1.5 Breach Notification

| Req ID | Obligation | Act Section |
|---|---|---|
| DPDP-BR-01 | Notify Data Protection Board of personal data breach | §8(6) |
| DPDP-BR-02 | Notify each affected Data Principal of the breach | §8(6) |
| DPDP-BR-03 | Breach notification timeline as prescribed by Rules | Rules Chapter (phased) |

## 2. Control → Evidence Mapping

### DPDP-DF-01 / DF-02 — Lawful purpose, notice, consent

| Control | Evidence |
|---|---|
| Data inventory and purpose map | `094_gdpr_erasure_audit_tables.sql` — erasure/restriction audit tables; `300_india_deployability_controls.sql` seeds `DPDP_NOTICE_PURPOSE_MAP` control requiring `evidence_uri` before real PHI |
| In-app notice | Patient app: privacy notice flow before ABHA linkage and OPD registration (requires counsel approval of notice text — Gap DPDP-G1) |
| Purpose mapping | `docs/india-deployment-readiness.md` §3 — each processing purpose must be mapped; operator checklist gate |
| Consent capture | `abdm_consents` table (ABDM consent artefacts); registration consent captured at patient creation; in-app consent withdraw flow (Gap DPDP-G2 — ease of withdrawal not yet audited) |

### DPDP-DF-03 / DF-04 — Consent quality: specific, not bundled

| Control | Evidence |
|---|---|
| Separate consent per purpose | ABDM consent artefacts carry purpose, HI type, date range, expiry — purpose-bound per NHA spec |
| No bundled consent | Architecture: ABHA linking, clinical care, AI processing, and marketing (none) are separate consent gates |
| Gap | Patient app registration flow: counselled-and-approved notice text bundling not yet audited by counsel — Gap DPDP-G1 |

### DPDP-DF-05 / DP-06 — Consent withdrawal

| Control | Evidence |
|---|---|
| Consent revocation in ABDM | `abdm_consents` table: `revoke` state; `abdmService.js` processes revocation callbacks from NHA |
| Patient-initiated withdrawal flow | Patient app consent dashboard surfaces active ABDM consents for revocation |
| Gap | For non-ABDM processing purposes (clinical care, AI), the consent withdrawal flow and its effect on ongoing care (stop AI, restrict data use without affecting mandatory medical records) is not yet formally documented and UAT-tested — Gap DPDP-G2 |

### DPDP-DF-07 / DF-08 — Data minimisation / purpose limitation

| Control | Evidence |
|---|---|
| Minimum-necessary data collection | `src/validators/` — express-validator chains enforce only declared fields per route; no catch-all body accept |
| Selective column retrieval | `apps/backend/CLAUDE.md` convention: explicit column names in all SELECTs; no `SELECT *`; `pwd`/`pin_hash`/`encrypted_password` never returned to client |
| PHI field encryption | `fieldEncryption.js` — only `SENSITIVE_USER_FIELDS` and `SENSITIVE_STAFF_FIELDS` are encrypted; others not stored unnecessarily |
| AI PHI limitation | Clinical AI: PHI never sent to external cloud model by default; local Ollama is the default provider; `CLINICAL_AI_DEEP_BASE_URL` egress allowlist |
| Analytics | `prismaReadOnly` routes analytics to read replica; Metabase reads OLTP today — DPDP minimum-necessary principle requires analytics copy to be de-identified (Gap DPDP-G3) |

### DPDP-DF-09 — Storage limitation / retention

| Control | Evidence |
|---|---|
| Retention policy | `300_india_deployability_controls.sql` seeds `DPDP_RETENTION_SCHEDULE` control; retention schedule requires hospital-specific `evidence_uri` |
| Erasure audit | `094_gdpr_erasure_audit_tables.sql` — tracks erasure/restriction requests and outcomes |
| Retention enforcement | Gap: no automated purge/archive mechanism at DB level with legal hold exception for mandatory medical records — Gap DPDP-G4 |

### DPDP-DF-10 — Technical and organisational security measures

| Control | Evidence |
|---|---|
| Encryption at rest (field-level) | `fieldEncryption.js`: AES-256-GCM envelope encryption (enc:v2) with per-record DEK wrapped under KEK (`fieldKeyProvider.js`); scrypt KDF; DEK wiped from memory after use |
| Encryption in transit | Cloudflare Tunnel end-to-end TLS; ingress-nginx TLS termination; internal cluster traffic |
| Access control | RBAC via `wrapAutoRBAC`; JWT HS256 with `jti`; token blacklist (Redis fast-path + DB fallback); NOSUPERUSER `vhhealth_runtime` DB role (WS0 B0.2) |
| Multi-tenant isolation | RLS policies on 283 tables (WS1 B1.1/B1.2); FORCE RLS; interactive `$transaction` tenant-scoped (WS1 B1.3) |
| Mobile PHI hardening | FLAG_SECURE on clinical screens (WS6 B6.1); encrypted SharedPreferences (B6.1); clipboard clearance; biometric re-auth on resume (B6.2); App Check activated (B6.2) |
| Audit trail | Hash-chained `clinical_audit_events` (migration 282); PHI access logging on all clinical routes |
| Pen test readiness | Self-SAST (Semgrep) and self-DAST (ZAP) run completed (WS1 B1.7); 0 self-found High at time of B1.7 run; external engagement `[flagged: procurement]` |
| Key management | `fieldKeyProvider.js` — pluggable KEK provider; rotation runbook in `docs/VAULT_SECRET_ROTATION_RUNBOOK.md`; no hard-coded keys |

## 5. Records of Processing Activities (RoPA) — Skeleton

The following is a minimal RoPA skeleton to be completed by counsel and the
hospital compliance team. Each row must have `evidence_uri` in the
`india_compliance_evidence` ledger.

| Processing Activity | Data Categories | Purpose | Legal Basis | Retention | Processor / Sub-processor | Cross-border? |
|---|---|---|---|---|---|---|
| Patient registration | Name, phone, DOB, address, blood group (encrypted) | Identity + care coordination | Consent (DPDP §6) / Medical emergency (§7) | 10 years (medical record law) | VH Health platform | No |
| OPD/IPD clinical care | Vitals, diagnoses, orders, MAR, investigations | Clinical care | Medical care (§7) | 10 years | VH Health platform | No |
| ABDM ABHA linkage | ABHA ID, phone | Health ID linkage | Consent (ABDM consent artefact) | Duration of consent | NHA ABDM gateway (India govt) | No |
| ABDM HI push | FHIR R4 bundles | Data sharing with HIU | ABDM consent artefact | Per consent expiry | NHA ABDM gateway (India govt) | No |
| Firebase OTP authentication | Phone number | Patient authentication | Consent at registration | Session duration | Firebase / Google | YES — requires DPA + §16 |
| Sentry error monitoring | Error stack traces (PHI-scrubbed) | Reliability / debugging | Legitimate use (§7) | Sentry retention policy | Sentry Inc. | YES — requires DPA |
| Clinical AI processing | PHI clinical context | Decision support | Clinical care (§7) | Duration of encounter | Local Ollama (default) | No (unless external model enabled) |
| Cloudflare R2 backup | Encrypted DB backups | DR / business continuity | Legitimate use (§7) | 30 days + WAL | Cloudflare | Confirm India-region bucket |
| Audit logs | Access metadata (not PHI fields) | Security / compliance | Legal obligation | 180 days (CERT-In) | VH Health platform | No |

## Implementation PR train — proposed, not authorized

The merge authority must confirm this split before PR 1 is pushed, and the owner must sign off S before implementation begins. Each PR starts from refreshed merged main in its own worktree, stays draft, carries `[full-ci]` on its tip, and receives an exact-head hand-back. Poll `gh pr view --json state` for MERGED before beginning the next PR; a green check or approved review does not mean merged. This lane never marks ready or merges. No production migration, activation or deployment is authorized by a document or implementation PR.

The suggested eight slices are consolidated where separately landing them would expose incomplete controls: lifecycle, governed authority, finalized logs, refresh and public response paths form one backend cutover unit. Task order below remains the work order inside that unit. A startup capability `cath_readiness_v2` defaults disabled and is evaluated once at route mounting for the entire new backend surface; it cannot enable an isolated Start route. Enabling requires a persisted successful migration/cutover marker and an approved tenant policy before the new workflow is admitted. This is a rollout barrier, not a readiness gate or a new role/signature prerequisite. Disabled means all existing cath routes use the unchanged legacy handlers and no new endpoint is mounted. Mixed old/new writers are prohibited.

# Unified Care Pathways S1b-b — Pathway Execution Spine Design

**Status:** implementation design, synchronized through frozen migration 584
**Baseline:** `df4dba1c3e80d503397b37195516ede638d2dc53` (PR #611 merge)
**Program authority:** `docs/superpowers/specs/2026-07-14-unified-care-pathways-program-design.md`
**Scope:** dormant substrate only; no pathway definition, handler, projector generation, scheduler, tenant flip, notification, or patient projection is activated

## 1. Outcome and safety boundary

S1b-b finishes the reusable execution substrate that S1b-a deliberately left dormant. Migrations 580–584 add the four pathway companion tables, an immutable transition ledger, typed task/SLA behavior, immutable definition/governance/checksum pins and terminal retirement evidence; the runtime adds a deterministic registered-handler executor, same-run graph enforcement, task/approval materialisation keys, a strict definition compiler, and a default-off pathway HTTP surface.

This slice does **not** encode D3–D7 or an external clinical/operational policy. D3–D7 were subsequently owner-approved on 2026-07-20, but their implementation remains in S2–S5 and does not retroactively change this dormant slice. It registers no clinical handler, ships no production or tenant pathway-definition seed, commits no active definition, changes no Stroke/STEMI authority, and introduces no OBGyn-specific pathway. The disposable comprehensive-test seeder transiently activates one synthetic definition only inside its transaction so the post-584 pinned-runtime graph is exercised; it retires that definition before commit and rejects any active synthetic definition. Governance fields and policy references are evidence-bearing substrate only: migration 584 supplies no D3–D7 default, external-policy resolver, recipient policy, clock value, or clinical threshold. Production active-mode execution remains fail-closed until S1b-c supplies reconciliation and activation evidence. A sealed active-mode capability exists only for `NODE_ENV=test` conformance tests; production cannot create it and rejects `active`. Shadow mode may persist hidden execution/reconciliation state but must not execute registered actions or create tasks, approvals, notifications, reminders, child instances, or patient-visible output.

## 2. State ownership

- `workflow_runs.status/current_step_key` and `workflow_steps.status` remain the sole mutable execution state.
- `tasks` own human-work state and `approvals` own approval state.
- `care_pathway_instances` supplies patient, encounter, episode, ownership, visibility, and closure context. It is not a second execution state machine.
- `care_handoff_instances` owns handoff-protocol state.
- `care_pathway_transition_events` is clinical-content append-only evidence. Canonical timeline rows are the patient/staff projection and clinical audit rows are the tamper-evident audit trail.

Every accepted pathway command appends canonical timeline, canonical audit, and pathway transition evidence in one tenant transaction. Most commands also change mutable state or materialise work in that transaction. A command that finds a task, approval, blocking child, or registered condition still waiting may instead append an idempotent wait observation with identical previous/new state and make **no** mutable-state change. State may never change without evidence, and an accepted command may never return without at least one transition intent. Generic non-pathway workflow mutations are not forced into this clinical evidence contract.

## 3. Database and live-rail hardening

Migration 580 creates the four tables and hardens the existing graph; migration 584 adds the final governance and runtime-pin invariants without changing that state-ownership model.

### 3.1 Existing graph

The migration first rejects:

- a task whose optional `workflow_step_id` belongs to a different `workflow_run_id`;
- an approval whose optional `task_id` belongs to a different `workflow_run_id`;
- a child task whose parent belongs to a different run when both declare runs;
- malformed or cross-tenant legacy `metadata.sla_instance_id` values;
- acknowledgement task/SLA lifecycle pairs whose task and clock disagree;
- duplicate resource-active tasks before the active-resource index is expanded to include `overdue`.

Deployment must run the same legacy task/SLA checks first as a **read-only, per-tenant preflight report**. Active orphaned, malformed, cross-tenant, unknown-semantics, rule-mismatched, source-mismatched, or clinically inconsistent links require clinical/operational reconciliation of the owning records before migration; terminal history without an active SLA claim and the explicit recognized policy-missing contracts below are not blanket failures. Migration 580 deliberately blocks unresolved debt: neither the preflight nor the migration may make an orphan fit by deleting a task/SLA or silently detaching its metadata link. An acknowledgement task that is acknowledged, completed, or cancelled while its SLA remains incomplete, or actionable while its SLA is terminal, must be reconciled from authoritative clinical evidence or the migration blocks. A terminal mortuary task likewise requires real release evidence.

Corrected-result reopen ancestry is a narrow migration-580 compatibility proof, not a status/comment inference and not the final acknowledgement authority. A current actionable critical-result task may follow a bounded multi-generation `reopened_from_task_id` chain of terminal predecessors only when every edge is monotonic and the predecessor has the same tenant, patient, linked SLA, and resource pair as its child. For this pre-580 history, the unique matching legacy SLA `reopen_history` entry must identify the predecessor and successor and preserve the predecessor clock; an exact system comment may corroborate that chronology but neither legacy field authorizes a clinical acknowledgement by itself. Comment-only, caller-authored, forged, non-reciprocal, ambiguous, cross-tenant/patient/SLA/resource, cyclic, non-monotonic, and over-bound chains all block for owner reconciliation. Each terminal predecessor keeps its exact existing `tasks.due_at` when present; otherwise migration 580 may use the unique matching legacy snapshot's `prior_due_at`, requiring equality when both exist and blocking when neither exists. The current rearmed SLA deadline is never copied backward into historical predecessors. After migration 581, the authority for a closed critical-alert generation is its exact immutable `lab_critical_alert_acknowledgement_receipts` row and version-2 alert/task/SLA/comment/timeline/audit chain; migrations 581/583 and the combined readiness audit never infer that authority from the current mutable SLA or `reopen_history` metadata.

Opening and post-lock preflights also detect historical critical-result generations committed without `reopened_from_task_id` or with a stale SLA `completed_by_task`. Because an overwritten clock cannot be reconstructed safely, migration 580 never infers generation one or its deadline; every unproven generation blocks for manual evidence reconciliation. This is a cutover classification, not an automatic repair or a durable replacement for the migration-581 typed generation receipt. Every accepted compatibility edge is same-tenant, same-patient, same-SLA, and same-resource.

Once the opening report is clean, migration 580 may perform only its explicit deterministic compatibility promotion/backfill for already-proven contracts. It does not manufacture clinical authority. Because traffic can write after the opening preflight, migration repeats compatibility and lifecycle validation after the task-table lock and normalization; this post-lock revalidation closes the opening-preflight race without trusting, deleting, or detaching intervening work.

It then adds database-enforced same-run composite foreign keys for task/run/step, approval/run/task, and parent/child task links; definition ID/key/version coherence; a deferrable run/current-step reference; unique step ordering; and at most one `in_progress|blocked` step per run.

Migration 584 makes governed-run classification depend on the **existence** of a `care_pathway_definition_governance` row, not on a caller-supplied pin and not only on `governance_status='approved'`. A generic workflow writer may create an unpinned run only for a definition with no governance row. Once any governance row exists, a fresh run must enter through the pathway executor with the exact active, approved, effective governance/checksum pin and must have exactly one exact pinned pathway companion plus one matching immutable `pathway_instance_created` event at transaction commit. Draft/under-review governance cannot be bypassed through the generic run surface. Existing approved or retired pinned runs remain classified as governed.

Migration 584 takes its maintenance-cutover `ACCESS EXCLUSIVE` table locks in one stable order, then installs shared transaction-scoped advisory fences for definition, approval, run-admission, governance, creation-event, and canonical-parent races. Mutation surfaces that could already hold a row or fence lock use nonblocking `pg_try_advisory_xact_lock`; governance actor rows use sorted `FOR SHARE NOWAIT`. Contention is translated to retryable SQLSTATE `40001` with a retry message instead of waiting into an opposite-order `40P01` deadlock. Creation-event admission may wait on its event fence because it cannot be the canonical-parent row-lock holder; canonical-parent update/delete takes the same fence fail-fast before revalidation.

The runtime uses the same distinction at the application boundary. A standalone start that owns its transaction retains blocking definition/start/episode locks so a concurrent lost-response retry can wait and replay. Any start composed inside a supplied branded transaction, including registered child fan-out, submits its complete sorted lock set to the fail-fast fence function. Prisma's driver-adapter SQLSTATE `40001` is mapped to `PATHWAY_START_SERIALIZATION_BUSY` with HTTP 409. Opposite child-definition orders therefore request a transaction retry and never wait into `40P01`.

### 3.2 Typed task/SLA contract

`tasks` gains:

- `workflow_sla_instance_id UUID` with a tenant-qualified foreign key;
- `sla_completion_semantics` in `none|acknowledgement|domain_evidence`;
- nullable durable `stage_occurrence_key`, unique within a tenant when present.

`approvals` gains an equivalent durable `materialization_key`.

Legacy valid SLA links are backfilled by text equality between `tasks.metadata.sla_instance_id` and `workflow_sla_instances.id::text`, but `metadata.sla_instance_id` and `metadata.sla_key` are deliberately retained and kept equal to the typed link and linked rule throughout a two-release rolling compatibility bridge. Task-row `BEFORE INSERT` and `BEFORE UPDATE` triggers are bidirectional: a recognized old writer's valid aliases populate the typed link, semantics, and database deadline, while a typed new writer repopulates both aliases for old replicas. The aliases and triggers may be removed only by a later cleanup migration after deployment evidence proves every old replica has drained. Orphaned, malformed, contradictory, and unknown aliases require reconciliation rather than automatic deletion or silent detachment. Classification comes from the joined rule and source binding, never from a name suffix or task title.

Separately, a PR #587 old-writer critical-result SLA rearm is crash-atomic in the database. A `BEFORE UPDATE` trigger preserves the exact terminal window and fresh corrected/amended sign-off as one database-owned pending generation; an `AFTER UPDATE` materializer creates or exact-matches one typed actionable successor in that same SLA statement, stamps reciprocal generation lineage, marks the receipt `linked`, and rolls back unless zero `pending_successor` generations remain. New-writer history is validated and enriched, never duplicated.

The rolling bridge also closes the old writers' initial task-materialisation gap. An incomplete, marker-free legacy SLA `INSERT` for `critical_result_ack` or `mortuary_unclaimed_body` must materialise exactly one owned task in the same database statement; atomic new writers stamp `task_materialization_contract='application_atomic_v1'` and remain responsible for their richer task. Critical-result materialisation recognizes only exact same-tenant/patient source shapes: `lab_result`, `investigations`, an accepted `task_candidate` with a route-capable owner role, a critical `clinical_alert`, or a `news2_score` of at least 5. `abnormal_triage` and `lab_autoverification` require manual rolling reconciliation, and every missing, ambiguous, or unsupported source fails closed rather than receiving a guessed owner. Mortuary materialisation requires `death_records:<integer text>`, a real same-tenant death record, and an earlier unclaimed `receive` custody event with no intervening release; it assigns the `MEDICAL_RECORDS` role and stores that receive event as initial evidence.

Preexisting PR #607 acknowledgements receive a compatibility promotion only from the exact same-tenant authenticated task receipt. During rolling deployment, a `BEFORE UPDATE` SLA trigger replaces the old writer's independent `NOW()` with `GREATEST(task.metadata.acknowledged_at, sla.started_at)`, promotes the authenticated actor to `completed_by`, preserves breach/escalation semantics, and records the submitted values. It deliberately performs a non-locking task read to preserve task-then-SLA lock order; malformed or mismatched receipts remain unchanged and fail deferred validation. This narrow promotion is not a general legacy auto-repair mechanism. The exact linked contracts are:

| Obligation                                   | Task side                        | SLA side                                                                           | Completion semantics                     |
| -------------------------------------------- | -------------------------------- | ---------------------------------------------------------------------------------- | ---------------------------------------- |
| Pathway workflow step                        | `workflow_step_id=<integer>`     | `source_table='workflow_steps'`, `source_id=<same integer as text>`                | explicitly declared by the compiled step |
| Critical result / cold-chain acknowledgement | exact `related_resource_type:id` | exact same `source_table:source_id`                                                | `acknowledgement`                        |
| Mortuary release                             | `death_record:<integer as text>` | `death_records:<same integer as text>` plus a real same-tenant `death_records` row | `domain_evidence`                        |

Unknown linked non-pathway rule codes fail closed. Migration 580 installs deferred constraint triggers that revalidate the binding when either the task, SLA instance, or mortuary owner row changes. When an enabled policy resolves, new producers pass the typed link and semantics explicitly; the rolling trigger exists only for mixed-version compatibility.

Human ownership is task-first, but the full intended owner invariant is not yet enforced. The current executor may populate both `assigned_to_uid` and `assigned_role`. Start validation proves only that a named UID is a same-tenant non-`PATIENT` user, and migration 580 accepts either a viable UID or a route-capable role; a viable role can therefore mask an inactive or non-route-capable named UID. The SQL role sets are kept identical to application route policy, and a valid role queue deliberately does not require a currently active holder in S1b-b because staffing coverage is S1b-c activation evidence. The critical-result application path resolves requested clinicians through the stronger policy, falls back to a route-capable role, and reassigns an already-actionable task whose named owner is no longer serviceable, but that application behavior is not equivalent to exclusive database enforcement. Generic clinical-inbox acknowledgement remains executor-blocked and no active pathway definitions exist. Exclusive owner resolution plus database conformance for active, route-capable named owners is required before activation.

An absent or disabled enabled-rule lookup returns `null`, including when `startWorkflowSla` is called with `strict: true`; strict mode makes invalid setup, database, and enabled-rule materialisation errors propagate, but it does not turn policy absence into an infrastructure error. A registered pathway stage therefore fails the whole command if its declared SLA cannot materialise, and the critical-result producer returns failure without creating an untracked task. Cold-chain and mortuary deliberately preserve human work under missing/disabled policy: they create an unlinked, deadline-free task with `sla_completion_semantics='none'`, no fabricated SLA instance, clock, or due time, and recognized compatibility metadata. Cold-chain stores `requested_sla_key='cold_chain_excursion_ack'` plus `sla_policy_status='missing'` without a legacy `sla_key`; mortuary stores the same marker for `mortuary_unclaimed_body` and also retains that `sla_key` for the old-release reader. The bridge's unlinked-degradation branch recognizes only the three producer contracts `critical_result_ack`, `cold_chain_excursion_ack`, and `mortuary_unclaimed_body`; it normalizes a recognized unlinked old-writer claim to the producer-specific missing-policy shape and rejects unknown or contradictory claims.

Generic acknowledgement completes an SLA only for `acknowledgement`. Generic completion and cancellation never silently complete a `domain_evidence` SLA; its strict domain-evidence completion entrypoint validates the registered evidence and completes the task/SLA atomically. The escalation sweep continues evaluating an acknowledged/in-progress `domain_evidence` task until that evidence lands. Cold-chain excursion acknowledgement and corrective-action recording both invoke the trusted task acknowledgement inside the same tenant transaction: when a typed clock exists, excursion acknowledgement, task acknowledgement, and SLA completion commit or roll back together; a degraded unlinked task has no SLA clock to invent or stop. Post-commit realtime emission occurs only after that transaction succeeds.

Cold-chain unit creation and update reject an `alert_roles` value unless every configured role belongs to the servicing `COLD_CHAIN_ROUTE_ROLES` policy. A legacy persisted invalid role can neither authorize the task nor receive a notification: live processing records a degraded audit shape, substitutes the safe department default role queue, and restricts outbound notification recipients to active users in that validated staff queue. A patient role is never a fallback or notification recipient.

Typed task/SLA lifecycle is enforced by deferred commit-time constraints. Actionable tasks require a clean incomplete clock; acknowledged or terminal tasks require the exact authenticated acknowledgement or direct-completion receipt; domain-evidence tasks require their exact mortuary-release or immutable pathway-transition receipt. Cancellation never completes an SLA and is rejected while the linked obligation is incomplete. A typed task cannot detach, change identity, or be deleted while its SLA survives, and deleting mortuary source evidence revalidates dependants at commit. Generic task APIs open `setTenantTx` when no transaction is supplied.

The deferred owner, source-binding, lifecycle, and receipt validators intentionally take no task-to-SLA or SLA-to-task cross-row lock. Their counterpart reads are non-locking, while assignment and receipt checks take only one-way `FOR SHARE` locks on the referenced user or `patient_access_break_glass` grant. Deferred dependency triggers on those referenced rows then revalidate dependants at commit. Conformance must cover both sides of concurrent task/SLA writes and user/grant mutation so this evidence hardening cannot recreate the prior task↔SLA deadlock.

The legacy death-record release entrypoint rejects before mutating `death_records` whenever a custody event, an active typed or degraded unclaimed-body task, or a mortuary SLA rail already exists; callers must use the custody release workflow. It retains legacy release behavior only when no custody/task/SLA rail exists. Custody immutability must be stated precisely: migration 414 blocks `UPDATE` on `body_custody_events`, while migration 580 revalidates `DELETE` only when the row is cited as a compatibility task's unclaimed-receive evidence or as an SLA's release receipt. Migration 580 does not claim a global delete prohibition for every custody event.

Manual, structured-panel, authenticated HL7 ORU, and ASTM result ingestion now commit the result, source/order advance, criticality decision, alert generation, exact task/SLA obligation, canonical evidence, and durable ingest-command/message receipt in one tenant transaction. Corrected/amended sign-off commits its signed clinical record, criticality delta, supersession/reopen generation, exact task/SLA, and canonical evidence in the sign-off transaction. Only transport fan-out remains post-commit: staff notification/realtime delivery and the existing outbound signed-result ORU feed may fail without rolling back the already-durable clinical obligation.

Critical-result acknowledgement has one authoritative transition. Both the lab-alert route and a clinical-inbox acknowledgement of its exact bound task use the same alert/task/SLA/comment/canonical transaction. Generic task acknowledgement fails closed for a migration-581 alert-bound task, including the admin workflow route, and only a transaction-required trusted lab entrypoint can cross that boundary after revalidating the exact tenant, current alert generation, patient, result, task, and SLA. New acknowledgements stamp technical `ack_contract_version=2` evidence consistently across task, SLA, task comment, canonical timeline, and canonical audit state. The existing nullable `read_back_method` contract is preserved: no server default is invented, and a supplied method is retained exactly in the durable/canonical evidence. Historical split state in either direction is never upgraded automatically from coincident legacy fields: unversioned task-ack/alert-open and alert-ack/task-open rows fail closed, remain unchanged, and block migration/deployment until an explicit owner-approved immutable reconciliation receipt exists.

The rule lookup deliberately relies on migration 352. Under a pinned tenant GUC, that policy exposes read-only global `workflow_sla_rules` rows (`tenant_id IS NULL`) while still preventing tenant writes to them. `startWorkflowSla` prefers an enabled same-tenant override and otherwise an enabled global rule, then inserts a tenant-owned SLA instance inside the caller's transaction. Regressions must preserve that visibility and the caller-specific missing-policy behavior above; they must not treat every missing or disabled rule as the same failure mode as a database/materialisation error.

### 3.3 Companion tables

`care_pathway_instances` has a UUID primary key, Pattern-A tenant default/RLS, a unique same-tenant workflow run, patient and canonical UUID encounter, pinned pathway key/version, immutable `workflow_definition_id`/`definition_governance_id`/`definition_checksum`, typed source episode, optional parent, owners/accountable role, clinical context/closure status, hidden-by-default patient visibility, durable idempotency key, timestamps, actors, and JSON-object metadata. The companion pin is a deferred composite foreign key to the same immutable `workflow_runs.pathway_governance_id`/`pathway_definition_checksum` identity. A partial unique index prevents duplicate `planned|active|on_hold` episodes.

`care_pathway_transition_events` follows the STEMI ledger protocol: UUID event, tenant/instance/patient/run, positive instance sequence, transition scope and key, stage, previous/new state objects, typed source, optional step/SLA/canonical references, actor-or-registered-system provenance, occurred and recorded timestamps, durable idempotency key, and JSON-object payload/metadata. Sequence allocation occurs only while the instance row is locked. The append-only trigger blocks delete and content mutation while permitting only referential `SET NULL` updates.

`care_handoff_instances` records sending and optional receiving instance/run/step, patient, typed source, urgency and policy due time without supplying values, sender and one recipient mode, the program status set, reasons, timestamps, task linkage, durable idempotency, and metadata. No referral-specific originator/ownership rule is encoded before D6.

`care_pathway_definition_governance` is one-to-one with a workflow definition and records owners, governance state, approval reference, approver/time, visibility-policy reference, effective dates, checksum, platform gates, and metadata. Migration 584 makes publication one-way: approved governance and its exact approval checksum receipt are immutable; retirement is a single terminal transition requiring an active same-tenant non-patient `retired_by`, `retired_at`, nonblank reason, non-extended `effective_until`, and an inactive definition. Retired governance cannot be reopened, deleted, or re-enabled; a new definition version is required.

The generic admin approval create/decide commands still exist for non-domain-owned approvals. They reserve `care_pathway_definition_governance` and `credential_privilege_grant` to their owning workflows and return `DOMAIN_OWNED_APPROVAL_KIND` before mutation; generic mutation of an approval attached to a pathway run separately fails with `PATHWAY_EXECUTOR_REQUIRED`. S1b-b exposes no pathway-governance publication/retirement/activation command. Thus “no generic approval command” is not an invariant; **domain reservation and executor ownership** are.

Governance approval evidence has a deliberate S1b-b limit. At publication, deferred checks prove that the JSON `approved_by` votes contain distinct currently eligible same-tenant non-patient users and valid vote timestamps, meet quorum, include the deciding actor, and belong to the exact definition approval. This approver/voter account lookup is publication-time only: the immutable receipt remains valid after a voter later changes role. Clinical and operational owners are current duties and continue to be revalidated while governance is approved; after retirement those owner identities are historical evidence and may later deactivate or change role without invalidating the retired record. A vote persists `uid` and `at`, but not a normalized immutable copy of the role held at vote time. The schema therefore **cannot prove that an approver held `approvals.required_role` when voting**, and S1b-b must not claim exact required-role attestation. Normalized vote/role evidence remains deferred governance hardening before production activation.

All new tables use UUID keys, tenant-leading indexes, child-side FK indexes, the tenant GUC default, and `ENABLE` plus `FORCE ROW LEVEL SECURITY` in migration 580. The existing workflow/task/death-record primary keys remain integer-family values. Only `tasks.workflow_sla_instance_id` is a UUID link; task/SLA source identifiers remain owner-table identifiers carried as text. The runtime must not cast arbitrary `related_resource_id`/`source_id` values to UUID or integer. It validates the mortuary integer shape and existence only through the owning table. Canonical timeline/audit UUIDs live on `care_pathway_transition_events`, not in legacy task IDs.

### 3.4 Lab ingest, corrected-generation, and governance-pin cutover (migrations 581–584)

Migration 581 makes each current lab critical-alert generation explicit and immutable: one alert is bound to one exact acknowledgement task/SLA, corrected/amended generations carry reciprocal supersession and sign-off lineage, and append-only reconciliation receipts distinguish an evidenced no-alert decision from missing work. Migration 582 gives authenticated HL7 ORU one immutable tenant+trusted-sender+message-control claim whose raw-message hash, actor/channel binding, OBX cardinality, result identities, critical-result partition, and active/closed alert/task/SLA arrays complete atomically. Migration 583 gives ASTM the equivalent exact analyzer-channel/raw-message claim, per-result link, verdict snapshot, and historical/live invariant validation. Historical reruns validate immutable ingest-time evidence and the current corrective-generation tail; they do not become invalid merely because an actor or analyzer is later deactivated or an order/specimen later reaches a terminal state.

Compatibility boundary: S1b-b preserves PR #587's shipped behavior for a lab result already marked critical. A corrected/amended sign-off still creates a fresh acknowledgement generation even when the current threshold evaluation is within range or unavailable. This slice does not implement normal-result auto-closure or abnormal-noncritical disposition: D4 and D5 were owner-approved only on 2026-07-20, and Diagnostics activation stays blocked until a follow-up design implements those decisions without either silencing a prior live instruction or leaving stale clinical work. This compatibility rule must not be generalized to investigations or new pathway stages; a currently noncritical investigation correction creates or re-arms no critical-result rail.

The generic `/api/v1/lab/interface/ingest` endpoint is ASTM-only. Authenticated HL7 ORU callers must use `/api/v1/lab/oru/ingest`, so no second receipt namespace can create a split crash/retry window. Numeric local order assertions must be positive in-range IDs and resolve exactly; absent or externally shaped alphanumeric identifiers preserve the pre-existing patient-only compatibility path because external-order mapping and ownership remain unsigned. That compatibility is **not** closure: an order-less result cannot be signed off today, and migrations 582/583 preserve its source identity. Every such ORU or ASTM receipt is therefore a hard activation blocker until an owner-governed reconciliation/linkage mechanism and migration exist. Manual `POST /lab/results` now requires `Idempotency-Key`; the exact in-repo production/UI caller sweep found none, but external callers are unproven and must be inventoried before cutover.

Migrations 580–584 are one non-rolling maintenance cutover. Before any deployment, run `lab:audit-care-pathway-spine-readiness` and `lab:audit-ingest-582-584-readiness` as an all-tenant privileged actor on the primary in their acknowledged repeatable-read/read-only modes. They report migration-580 task/SLA/receipt debt; migration-582/583 ingest identity, sender/analyzer, order-link, critical-rail, and corrected-tail debt; and migration-584 governance/pin schema and tracker coherence with bounded non-PHI evidence. A PostgreSQL 18 production-clone rehearsal is independent mandatory evidence, not a substitute. During maintenance, old replicas are drained, the pending set must be exactly `[580, 581, 582, 583, 584]`, or exactly `[582, 583, 584]` only when tracker evidence proves 580 and 581 landed together in a documented compatible release. Partial tails, omitting 584, or treating 584 as preinstalled while 582/583 remain pending are blockers. Migration-581 reconciliation then runs as the migration owner or a `BYPASSRLS` role; post-schema audits must be clean before traffic resumes. The exact sequence and rollback boundary are in `apps/backend/docs/RUNBOOKS/lab-oru-582-maintenance-cutover.md`. This PR performs no deployment or tenant/pathway activation.

## 4. Definition compiler and runtime registry

The production registry is one immutable, exact-match, empty registry at version 1. Tests may construct isolated registries, but each positive version may be bound to exactly one object identity in a process; a lookalike object or second registry at the same version is rejected. Every non-replay command carries the **same exact registry identity and `registry.version`** through system-actor validation, definition compilation, handler resolution, nested child starts, and transition recording, then pairs them with the compiled governed-definition checksum. The command fingerprint includes the registry version and normalized command/start inputs. Migration 584 makes the target instance and run separately and immutably pin definition ID, governance ID, and checksum; compilation verifies the persisted checksum, and emitted evidence stores the registry version and checksum. Replay intentionally returns the stored committed snapshot before recompilation only after `assertPathwayReplayDefinitionPinTx` proves the instance/run/definition/governance/checksum joins, exact approval checksum receipt, and stored creation/runtime-event pins still agree. No nested call may silently fall back to the production registry.

A fresh start requires an active, approved, currently effective definition and writes both immutable pin sets. Retirement prevents every fresh start and requires the definition kill switch to be off, but it does not strand already-created clinical work: an existing run whose exact approved-or-retired pin remains intact may continue through the executor to a terminal outcome, and its exact committed replay remains available after current PHI authorization. Neither completion nor replay may substitute a newer definition/governance row or checksum.

A registered system actor is a frozen identity-sealed object created by that same registry. Its versioned `systemKey` must be registered; its projector-causation `sourceEventId` is mandatory and BIGINT-safe without JavaScript number coercion; optional `causationId` is normalized once; and its independent immutable `signalContext` must contain canonical `sourceResourceType`, `sourceResourceId`, and `occurredAt`. Copying the object destroys the seal. A system command supplies only signal kind and payload: the executor derives source lineage and occurrence time from the sealed context and rejects caller-spoofed signal fields. A top-level system start must use `triggerKind='event'`; it likewise rejects trigger-payload lineage and derives the creation event's source/time from the sealed context. The production empty registry therefore cannot construct an executable system actor.

The compiler preserves S1b-a JSON hardening and accepts only the v1 subset:

- array order is the normal linear path;
- built-in task and approval work semantics;
- versioned registered condition/evidence, computation-only action, and child-fan-out handlers;
- declared, forward-only conditional exception targets;
- declared child pathway key and relationship classification;
- no stored code, expression, SQL, URL, arbitrary target, loop, or join.

Task and approval steps are **pure human gates**: they may materialise only their task/approval work and may advance only from the persisted work state. No action handler or child fan-out may execute as an undeclared gate-exit side effect. For `domain_evidence`, a trusted projector/domain integration invokes `completePathwayTaskAndExecuteFromRegisteredEvidence`, the sole production orchestration helper. Before its first await, the combined helper normalizes and freezes one immutable command envelope containing the tenant/target, normalized actor and signal, executor-derived idempotency key, activation-evidence capability, and normalized domain-evidence operation. Replay lookup, task/SLA completion, fingerprinting, activation checks, canonical writes, and pathway execution consume that same envelope; the helper never rereads mutable caller input for actor, signal, key, or activation authority after asynchronous work begins. The executor alone mints the object-identity capability held in its private `WeakSet`; callers cannot construct or obtain it, and the only exported mint is `NODE_ENV=test`-guarded. In one branded tenant transaction, the helper uses that capability to call the internal `completePathwayTaskFromRegisteredEvidence` primitive, strictly completes the exact task and linked SLA, and then executes the pathway command. The primitive validates exact pathway/instance/run/step context, `domain_evidence` semantics, and the `workflow_steps:<step id>` SLA source binding, then retains the full normalized evidence in the SLA completion metadata and task audit comment. The executor emits a canonical `domain_evidence_task_completed` transition with the exact task/SLA identifiers and statuses, but its pathway/canonical event carries only a compact provenance-bearing evidence reference and SHA-256 `evidence_fingerprint`, not a duplicate raw evidence payload. An exact-evidence retry is idempotent and preserves the original SLA `completed_at`; mismatched prior evidence fails closed.

Before commit, the helper requires the canonical task-completion event and re-evaluates the governed condition as satisfied. A task gate must produce its evidence-backed `step_completed`; an approval gate may instead remain `approval_waiting` only when the evidence is satisfied and the approval is still pending. Unsatisfied/blocked evidence, an evidence-selected forward exception, a mismatched task/run/step/handler, a missing canonical postcondition, or any audit/canonical write failure rolls back task completion, SLA completion, completion comment, runtime changes, and transition evidence together. Condition satisfaction alone never invokes the primitive or completes work. Generic forward exceptions remain allowed for ordinary commands only after all materialised human work is terminal; they may not be used to turn a rejected evidence-completion postcondition into success. Generic non-pathway approval commands remain available only within their unreserved domain; this slice exposes no generic **pathway** work-item completion/decision command, and later pathway integrations must enter through the sole executor orchestration surface.

Reusable task/approval definitions cannot carry a static `due_at`; the compiler requires their deadline to come from the linked SLA rule. `startWorkflowSla` computes the canonical deadline in PostgreSQL from database `NOW()` and the enabled rule, and the task `INSERT` selects that exact `workflow_sla_instances.due_at` value in the database rather than round-tripping it through a JavaScript `Date`. A caller-supplied due time for a typed task is rejected, and both deadlines must exist and remain exactly equal or the whole command fails. This exact-equality rule applies to the current actionable task and current rearmed SLA. A terminal corrected-result predecessor is historical evidence: its migration-580 deadline follows the exact preserved task/unique legacy clock-snapshot precedence above and must never be overwritten with the current SLA's rearmed deadline; post-581 closure authority remains the typed immutable acknowledgement receipt.

For `taskService` raw-driver writes, caller-originated instants bind as epoch milliseconds and PostgreSQL reconstructs `timestamptz` with `to_timestamp(ms / 1000.0)`; durable JSON receipt timestamps are formatted in SQL as explicit UTC `...Z` strings. Directly binding JavaScript `Date` or timestamp text is prohibited because process-timezone reinterpretation can change the clinical instant. SLA-derived task deadlines remain direct database selections to preserve microseconds.

A declared forward exception completes the source step, CAS-skips each intervening pending step with `forward_exception_bypassed` outcome/evidence, then activates the target. Skipped steps execute no handler and materialise no work; any skip or evidence failure rolls back the whole command.

Condition handlers have a split contract. Optional `loadEvidence({ tx, ...readContext })` reads in the command's existing tenant transaction so it can see preceding uncommitted work. It runs inside a savepoint that is always rolled back and released before evaluation, discarding ordinary transactional writes. This is rollback isolation, **not** a database-enforced read-only capability: code-reviewed loaders must be side-effect-free and must not use sequences, session mutation, transaction-control SQL, or externally effectful database functions. The normalized frozen JSON result is passed to `evaluate({ ...readContext, loadedEvidence })`; `evaluate` receives no transaction and is pure.

All handlers receive deep-frozen graph snapshots. Registered actions are computation-only in S1b-b: like child fan-out and pure condition evaluation, they receive **no raw transaction or query capability** and may return only normalized data for the executor to record. The condition evidence loader alone receives the branded transaction, only under the rollback contract above. Around an action, the executor still hashes the full parent runtime, governed definition, child run/step/task graphs, and transition ledger count/sequence, then re-locks and reloads them after the handler; any delta fails with `PATHWAY_ACTION_RUNTIME_MUTATION_FORBIDDEN` before evidence flush. That graph check is defense-in-depth, not permission to write. Code-reviewed allowlisted capabilities for atomic domain writes remain deferred as a hard S1b-c and production-activation prerequisite.

Activation compilation rejects every unresolved handler, unsupported kind, duplicate key/order, invalid target, unclassified child, unsafe SLA contract, or checksum mismatch. Existing handler IDs are immutable; changed behavior requires a new versioned ID. Technical, non-clinical safety caps are part of the v1 contract: at most 128 steps, 16 exception targets per step, and 16 child rules per step; the compiler rejects a deterministic auto-chain whose static transition-intent estimate, including the worst-case command child-fan-out reserve, can exceed 512. Every guarded definition, command, evidence, and handler/runtime JSON value is also limited to depth 32, 4,096 visited nodes, and 65,536 serialized UTF-8 bytes. These are execution resource bounds, not clinical thresholds.

## 5. Executor contract

The executor is the only authoritative pathway state mutation surface. HTTP and future projector adapters submit commands; neither supplies a desired run status or arbitrary current step.

```js
executePathwayCommand({
  tenantId,
  pathwayInstanceId,
  idempotencyKey,
  signal,
  actor,
  tx,
  registry,
});
```

Actors are discriminated:

```js
{ kind: 'user', uid, roles, primaryRole, authorizationMode, overrideReason?, breakGlassId? }
{ kind: 'system', systemKey, sourceEventId, causationId?, signalContext: { sourceResourceType, sourceResourceId, occurredAt } }
```

Routes construct user actors only from `req.user` and an always-enforced server-side patient-access decision. Patient PHI authorization is independent of both care-team rollout mode and pathway `off|shadow|active` execution mode: neither mode system may downgrade a denial, and execution shadow never permits fail-open patient access. A denied request reaches neither the pathway read nor the executor and receives no pathway PHI. Patient-access break-glass is the only override; it must already carry a verified audit id and reason and remains audited. Roles are canonical uppercase values, and `primaryRole` must be one of them. The create route also derives `triggerKind='manual'`, an empty trigger payload, and source episode `patient:<patient_uid>` or `patient_encounter:<encounter_uuid>` from the guarded patient context. A top-level manual start forces owning clinician to the authenticated actor, clears team ownership, and takes accountable role from `primaryRole`; conflicting caller-selected owner/team/role values fail closed. A user cannot supply actor, trigger, source-resource lineage, or `occurred_at`, and cannot establish a parent link; `parent_instance_id` succeeds only through the executor's sealed child-start capability. Projector adapters will construct sealed allowlisted system actors with separate causation and signal context; their command signal may contain only kind/payload. Event payloads are evidence, never authority.

### 5.1 Immutable command lineage and replay

Every start/command requires a tenant-scoped raw idempotency key at its caller boundary, but only an executor-derived canonical internal namespace may pass into persistence or evidence:

- user: `u:<uid>:sha256(operation + raw_key)`. The target and payload are deliberately absent. Reuse by the same user of the same raw key for the same operation therefore reaches the same canonical command key, and a changed target, payload, actor context, or other command-fingerprint input conflicts instead of creating a second command;
- sealed system: `s:sha256(systemKey + sourceEventId + operation + business_target)`, independent of the supplied raw caller key. The same sealed source event, operation, and business target deduplicate; any changed fingerprint or sealed lineage conflicts;
- child: `c:sha256(parent_instance + run + step + rule + child_business_identity)`, where child business identity includes the deterministic child ordinal, pathway/definition, and source episode. Nested calls cannot substitute a caller namespace.

The raw client key is transient input and must never persist in a pathway instance, transition event, canonical timeline/audit evidence, metadata, or result snapshot. Transition evidence stores only the canonical key, a SHA-256 fingerprint over the normalized operation, target, actor, signal/source, registry version, and inputs, plus a contiguous zero-based effect ordinal under a tenant-wide uniqueness constraint. A replay remains subject to the current always-enforced route PHI authorization. After that authorization succeeds, an exact committed replay may return its immutable stored result snapshot and events before current pathway-mode evaluation so a lost response is recoverable even when the pathway is now `off`. It never recompiles, evaluates handlers, executes effects, or mutates state.

User commands carry server-derived manual provenance and cannot assert source lineage. System commands require the sealed actor's immutable projector `sourceEventId`, optional `causationId`, and independent source/type/time signal context; transition evidence persists the causation and executor-derived signal lineage with registry version and governed definition checksum. Transition rows are append-only, so lineage cannot be restamped after commit.

### 5.2 Transaction and transition-intent protocol

Within the supplied projector transaction or one `setTenantTx`, the executor:

1. validates tenant, actor, signal, idempotency key, JSON shape, and the exact registry identity;
2. locks instance then run, child instances, steps, linked work items, handoffs, and SLAs in one fixed order;
3. returns a prior committed result for the same idempotency key and command fingerprint, or conflicts on key reuse with different input;
4. loads the pinned definition/governance checksum and compiles it against that same registry;
5. verifies graph/current-step invariants and signal ownership;
6. loads evidence through the rolled-back savepoint, calls pure evaluation, and builds a frozen stage plan;
7. applies CAS state changes and idempotent task/approval/child effects while recording only frozen transition intents in a private command buffer;
8. freezes the result snapshot and submits the private ordered buffer of frozen transition intents to one batch append session; array order owns contiguous effect ordinals, and each intent writes the canonical timeline/audit pair before its pathway transition row in the same transaction;
9. commits, after which outbox-driven external work may proceed.

Crash before commit leaves nothing. Replay after commit returns the prior effect without duplicating work. Handler or canonical-write failure rolls back state, work items, evidence, and a future projector inbox acknowledgement together. Interactive transaction callback business errors, including authorization, conflict, CAS, and governed-postcondition failures, propagate to the caller but cannot consume or open the global-per-client database circuit breaker; only positively classified database/driver infrastructure failures count toward that breaker.

The batch append session locks the instance and tenant command key, loads the replay group once, prevalidates all intents, and reads `MAX(sequence_number)+1` once. A private WeakSet-sealed session allocates contiguous instance sequences. A complete committed group replays exactly; a partial or differently sized group fails closed rather than resuming. Any mid-batch canonical failure aborts the caller transaction, including canonical/transition rows written earlier in that batch. The public single-event append remains for atomic pathway start and retains the same replay safeguards.

Runtime resource caps are 32 resolved children per rule, 64 per stage, and 64 newly-started children across the entire command; 512 aggregate child workflow steps across internal child starts; 512 transition intents; and 384 applied stage plans. JSON crossing the guarded compiler, executor, evidence, or handler/runtime boundary has the shared technical ceiling of depth 32, 4,096 visited nodes, and 65,536 serialized UTF-8 bytes. The child-step budget is WeakMap-sealed and propagated/debited through internal child-start capabilities, so handlers cannot reset it by nesting. Breaching a cap aborts the whole transaction. These caps bound hostile or defective registered behavior and do not define pathway clinical policy.

### 5.3 Child relationship semantics

- `blocking`: must resolve at least one child; the parent stage waits for every blocking child to complete and blocks on a cancelled/entered-in-error child.
- `nonblocking_with_named_owner`: every child must name an owning clinician or team; the parent may advance after durable dispatch while the child continues independently.
- `informational`: records the linked child without governing parent closure.
- `ownership_transferring`: the classification is reserved, but the compiler rejects every definition that declares it until destination-acceptance evidence and originator/ownership-transfer rules land under D6 and S3. Runtime checks remain a fail-closed defense for any impossible precompiled value.

All child starts inherit the parent tenant, patient, encounter, actor, registry, transaction, and active-test capability; use the executor-derived `c:` canonical idempotency namespace over parent/run/step/rule and deterministic child business identity; and persist the relationship in child metadata/transition evidence. They do not by themselves create a `care_handoff_instances` acceptance record.

## 6. Routes and bypass prevention

`/api/v1/care-pathways` is clinical-staff gated, sanitized, guarded by always-enforced patient ABAC, and PHI logged. That authorization gate is independent of both care-team rollout mode and pathway execution mode. A denial never reaches an instance read or executor call, including when either mode is `shadow`; execution shadow governs effects and visibility only and never authorizes patient access. An audited, verified break-glass id and reason remain the sole override. Create ABAC resolves only `body.patient_uid` and rejects every request-query patient-selector alias; any resource-resolution failure is authoritatively unresolved and cannot fall back to query or body selectors. Instance create/command routes accept idempotency keys and actor identity only from authenticated context. Manual source episode, trigger provenance, owner, and accountable role are server-derived as described above. They never accept caller-selected status, step, sequence, patient attribution, system lineage, handler provenance, or canonical IDs.

- `off`: reject every fresh start or command without mutation; after current PHI authorization succeeds, an exact committed replay may return only its immutable stored snapshot under §5.1;
- `shadow`: only after current PHI authorization succeeds, permit hidden state/evidence; suppress registered actions, tasks, approvals, child instances, notifications, reminders, and patient output;
- `active`: production rejects with activation-evidence-unavailable until S1b-c lands; only the sealed test capability may exercise active effects in conformance tests.

The security resource resolver learns `care_pathway_instance` so instance routes resolve patient context before access. Direct generic run/step/task/approval mutation entrypoints reject rows linked to a pathway instance; later pathway slices integrate authorized work-item commands through the executor.

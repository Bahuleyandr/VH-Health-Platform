## 1. Problem and scope

The platform holds **four independent reprocessing loops with four incompatible identity models**, built at four different times:

| | cath (Plan 2, mig 765) | dialysis (mig 418) | OT/CSSD (migs 421–423) | linen (migs 473–474) |
|---|---|---|---|---|
| identity | system-minted `device_tag` `RP…` | operator-typed `dialyzer_serial` free text | `set_code` + `barcode`, operator-supplied | none (quantity) |
| grain | one row per physical device | one row **per session** | one row per set + one issue row per OT case | per laundry cycle |
| state machine | 6 states, `DEVICE_ACTIONS` from-lists | 3 flat statuses | 9 on the set, 7 on the issue | 5 on the cycle |
| cycle ceiling | `max_cycles_snapshot`, DB CHECK | `reuse_cycle_count` 0..100, typed, no policy | none | none |
| serology gate | full (`resolveReuseStatus`) | none — parallel `dialysis_patients.*_status` columns, never consulted by the reuse path | none | none |
| sterilisation evidence | manual CSSD mark, no load link | `integrity_test_result` pass/fail, `disinfectant` free text | `sterilization_loads` with BI/CI/mechanical indicators | none |
| per-patient dedication | pooled | recorded (`patient_uid`) but never enforced | pooled | pooled |

Plan 4 is **convergence, not extension**: one register, one policy shape, one state machine, one serology gate and one CSSD queue serving dialysis and OT, with the cath register left where it is. Linen stays quantity-based and is out of scope.

The three defects this closes, in order of clinical weight:

1. **Dialysis has no serology gate and two serology records that disagree.** `dialysis_patients.hbsag_status / hcv_status / hiv_status` (168:45-50) drive `isolation_required` and the today board, but a reactive HBsAg signed off in the lab updates `patient_bloodborne_markers` (Plan 1) and *not* those columns. A patient the platform knows is reactive can sit on the board as non-isolation. The dialyser reuse path (`dialysisService.recordReuseRegister`, :928-999) reads neither record. This defect has two halves and two owners: *which record the roster reads* (the derivation) is the Phase 1 lane's, and *the reuse path reading no record at all* is this lane's — closed by consuming Phase 1's resolver (§3.3).
2. **The dialyser cycle count is whatever the operator typed.** `reuse_cycle_count` is validated only against `dialysis_sessions.reuse_count`, a number the same client wrote on the previous call (:945-957). Nothing links two register rows carrying the same serial; nothing stops one serial appearing under two patients; there is no maximum, no TCV rule and no agent/contact-time record.
3. **OT sets carry no cycle count, no exposure flag and no policy**, and a set used on a reactive patient is returned and re-issued like any other. Sterilisation evidence exists (`sterilization_loads`, 422) but cath devices are not on it, and a failed load does not touch a set already issued.

### 1.1 Consumers and non-goals

**Consumers of this lane:** dialysis (**dialysers only** — bloodlines are **removed from this release**: one usage per session cannot model a bloodline set beside a dialyser, and a bloodline is single-use in every Indian unit this platform serves; a later release models them as slots if a tenant ever needs them, §10) and OT (instrument sets and trays; **procedure packs are tracked but can never be made reprocessable** — a `reprocessable = true` policy row is refused for them by CHECK, §4.2). Cath keeps `cath_reprocessable_devices` untouched (D1b); §2.6 states the seam a later cath migration would use.

## 2. Decisions

The owner's decisions are fixed; the reasons recorded here are the scouting brief's, kept so the migration header can state them inline.

- **D1 — Owner references are typed, nullable per-domain FKs plus `CHECK (num_nonnulls(...) = 1)`.** The pattern is already in production on `surgical_implants` (`565:54-58`, `surgical_implants_source_check`). A `(ref_type, ref_id)` string pair cannot be a foreign key; three sibling registers cannot share a queue. Every arm is a tenant-pinned composite FK (§2.4).
- **D1b — Cath stays in `cath_reprocessable_devices`.** Two registers, one service shape, one queue with a domain filter. The seam for a later cath migration is §2.6.
- **D2 — The register is patient-blind.** Per-patient dedication of a dialyser lives on the dialysis link row (§2.5), never on `reprocessable_devices`. This is what keeps `/api/v1/cssd` free of a PHI logger and keeps the CSSD queue out of the serology disclosure blast radius.
- **D2b — Domain is a fixed enum**, `dialysis` and `ot`, with `cath` reserved. Per-domain rules are code, not configuration; a tenant seeding a "Nephrology 2" department must not create a fourth rule set.
- **D3 — Dialysis machines do not enter the register.** A minimal `dialysis_machines` table (§2.7) carries the routing group (`isolation_group`, D11 = NO); isolation is **warn-only with a recorded override**, mirroring `set_issue_log.warn_only / enforcement_enabled` (423:27-28), with a per-tenant switch to `block` for units that have tagged their machines. **Review 2026-09-06:** `block` has **no escape routes** — in block mode an unregistered machine and an unmapped class are refusals, the switch to `block` is refused until the mapping is validated against active machines, and the emergency exception is an explicit authorised workflow with its own role set and audit (§3.4).
- **D5 — OT scope is instrument sets plus the sterilisation-load evidence FK on `surgical_implants`.** Implant reuse is out of scope.
- **D6 — Dialysis converges: mint device identities for dialysers; `dialyzer_reuse_register` stays as the statutory log and gains `device_id`.** `reuse_cycle_count` becomes derived from the device, which is the defect being closed. Two behaviour changes follow and are flagged in §4.2: a client-typed cycle count that disagrees with the device is refused, and a register row stops being freely re-writable once the device has moved on. **Review 2026-09-06:** the record also carries the **release criteria** (§4.2a, §5.1): a reprocessing record whose mandatory evidence is missing settles the usage but does **not** release the dialyser (`release_status = 'not_established'`), and a settled record is followed by **append-only attempts** (§4.14), never a rewrite.
- **D7 — Sterilisation evidence is load-driven for OT and not for dialysis.** OT sets are already on `sterilization_loads` (`set_ids`, `instrument_sets.last_passed_load_id`, `set_issue_log.sterilization_load_id`); a passed load increments the set's device cycle and a failed load quarantines it. Dialyser reprocessing is a chemical reuse-room process recorded on the statutory row, not an autoclave load. **Review 2026-09-06:** a passed *status* is not a processing *event* — evidence identity is a durable per-device `device_processing_events` row (device × load, exactly once, with its applicability window), written by ONE load-outcome handler that both `createSterilizationLoad` (which can create a load already `passed` or `failed` — verified on `main`: `deriveLoadStatus` returns `passed` when `completed_at` is set and every indicator passed, and the creation path then UPDATEs `instrument_sets` and `set_issue_log` directly) and `transitionSterilizationLoad` call (§5.2). Both sides of the evidence chain are kept: the event that made a set ready **before** a use is pinned immutably on the usage, and the event **after** it is recorded separately.
- **D8 — Billing unchanged.**
- **D9 — External identifiers are accepted alongside the minted tag.** `manufacturer_serial` (dialysers) and `hospital_asset_id` (the OT set barcode is copied here) are unique per tenant and domain when present; the minted `device_tag` is always present.
- **D10 — DECIDED separately per role (review 2026-09-06): D10a `DIALYSIS_TECHNICIAN` = NO; D10b `BLOOD_BANK_STAFF` = NO; D10c `BLOOD_BANK_TECHNICIAN` = NO.** None joins the serology-detail audience in this lane. A dialysis technician receives the three-valued status, non-clinical warning codes and `required_group`, which is sufficient to route without exposing the marker. The two blood-bank roles have no Plan 4 clinical-detail surface, so broadening their platform-wide serology access would exceed this lane. This is three explicit decisions, not a bundled inference from provisioning. `NON_ASSIGNABLE_HUMAN_ROLES` (`rolePolicyGraph.js:343-363` on `main`) contains `DIALYSIS_TECHNICIAN` and `BLOOD_BANK_STAFF` but not `BLOOD_BANK_TECHNICIAN`; non-assignability is not proof that nobody holds a role. `scripts/role-assignment-census.mjs` (§7.6) therefore counts actual active assignments per tenant for all three before implementation hand-back and clinical activation. Any future widening is a separate reviewed change to the canary-pinned allow-list. The D11 routing-payload test uses a fixed role fixture and cannot become vacuous if that future change occurs.
- **D11 — DECIDED — NO (owner, 2026-09-06, via the merge authority). May a routing role learn *which* marker isolates a patient, or only *that* one does? Only *that* one does.** Whoever puts a patient on a machine must know the patient needs an isolation machine; the *reason* is not named to that role. The NO branch **ships and is the design, not an option**: (a) `dialysis_machines.isolation_group` — a tenant-defined label ("Bay 1", "Red side") carrying no clinical meaning, `VARCHAR(40)`, **nullable, where `NULL` is a general machine** — **replaces** `isolation_class` as the machine's routing key in migration `NNN`, in `listMachines` / `createMachine` / `PATCH /machines/:id`, in the OpenAPI `DialysisMachine` schema and in the Admin and Staff machine forms (§4.6, §6.1, §6.7, §6.8). (b) The class → group mapping lives in the per-tenant isolation settings as `reprocessing_domain_settings.isolation_groups` (§4.1), a JSONB object keyed by the four marker classes — e.g. `{ "hbsag": "Bay 1", "hcv": "Bay 2", "hiv": "Bay 2", "isolation_mixed": "Bay 3" }` — written only through `PUT /api/v1/reprocessing/domains/dialysis/settings` under `ISOLATION_GROUP_ADMIN_ROUTE_ROLES` = `REPROCESSING_POLICY_ROUTE_ROLES ∩ {INFECTION_CONTROL_OFFICER, ADMIN, SUPER_ADMIN}`; `QUALITY_OFFICER` (also on the governance mount) reads it and cannot write it, and `DIALYSIS_TECHNICIAN` — which lives on `DIALYSIS_ROUTE_ROLES` and on no governance set — **never reaches the mount at all**. A save naming a group that is on no registered machine **warns**; it does not refuse (a unit may map its bays before it tags them). (c) `assessIsolationTx` / `evaluateIsolationForSessionTx` still call the resolver with `includeIsolationClass: true` and map class → group **server-side** through those settings; the comparison is `required_group` vs `machine.isolation_group` (§3.4). (d) `isolation_warnings[]` entries carry `{ code, machine_id, severity, required_group }`. **`required_group` is the live key and `required_class` is RETIRED**: it is not in `computeIsolationWarnings`' output (the marker class survives only as an unnamed local inside it, used to index the map), not in the internal isolation object, not in the `DialysisIsolation` schema (`additionalProperties: false`, which lists `required_group` and never a class), not in the mismatch or blocked messages, and not in the `dialysis.session.isolation_evaluated` metadata — all of which name the **group** (§7.2). (e) **Review 2026-09-06 — widened to EVERY writer and BOTH domains:** the platform register carries **no marker name anywhere**. `reprocessable_devices` has **no `exposure_markers` column at all** (§4.3): the exposure fact on a device is the boolean `exposure_flag` (historical, never cleared) and the operational restriction is a **hold row** (§5.5); the *which-marker* evidence lives only on the hold's pointer to the audience-gated marker row (`patient_bloodborne_markers`, the existing record behind `roleSeesSerologyDetail`). This closes the contradiction the owner found: the late-reactive handler (§3.2) no longer writes `'Late reactive <marker> …'` into `quarantine_reason`, no longer appends a marker to a device, and its audit metadata carries a hold id, not a marker. `quarantine_reason` becomes a **non-clinical reason code** from a fixed vocabulary (§4.3), and free text goes to the hold row. **The OT arm is marker-free too** — the owner asked for dialysis; making the register uniform costs nothing, removes an asymmetry the canary would otherwise have to special-case, and the OT evidence is the same hold → marker-row pointer (approved as the uniform two-domain representation). The CSSD queue reads the flag and universal precautions apply. (f) Staff renders `required_group`; the `required_class` string key is dropped from the five-locale block (§6.8). (g) **Two** server-side callers pass `includeIsolationClass: true` (review 2026-09-06 changed this from one): `assessIsolationTx` (machine routing, class → group) and `reuseEligibilityTx` (the pathogen-specific reuse matrix, §5.3, which cannot be pathogen-specific without the class). Both are in-process decisions; neither serialises, snapshots or audits the class, and the plan pins the count at exactly two by name (§8). **Revision 2:** the routing semantics remain, but §3.3 makes a versioned Phase 1 contract-amendment request for protected evidence references, dates/currency and the full internal isolation profile. Stage 2 is blocked until the owning lane accepts that interface; Phase 1 still does not depend on Plan 4 tables. **Costing history, kept so the decision is legible:** YES would have cost nothing — `isolation_warnings` regains `required_class` and the design is what review round 1 settled on as Fix-6; NO costs one column swap and one settings block, and that is what shipped. **The limit the owner priced honestly (dev-1b):** under NO the mapping is opaque in the *data*, not in the *world* — a technician who sees which patients route to "Bay 1" learns the cohort within a week, and "Bay 1 is the hep B bay" becomes ward knowledge whatever the payload says. That is an inference risk, not a disclosure, and it did not argue against the design (routing has to happen somewhere physical): `isolation_group` **reduces the blast radius** — no marker in an API response, a log line, an audit row or an export — without *eliminating the knowledge*, and it was chosen for the former, not in the belief that it achieves the latter. Review round 1's Fix-6 ("do not blank `required_class`") is **SUPERSEDED**: that round reasoned the class was recoverable anyway (`GET /machines` published every machine's class and the two mismatch codes narrowed it by elimination), which is an argument for this relabel rather than for shipping the class — under `isolation_group` the same elimination recovers a bay name and nothing more.

Decisions taken by this spec within those:

- **Cancellation restores only proven-unused readiness.** Scheduled/no-show cancellation closes the usage through `restoreUnusedCaptureTx`, not the processing release path. `sealed_unopened` may restore `available` only when the prior readiness remains valid and every obligation is clear; `not_connected` proves no patient use but requires a fresh cycle and clears episode residual evidence; a hold lands the device `quarantined`. In-progress use terminates through `completeSession(...early_termination...)` into a non-available returned state (§5.1, §5.6).

- **Two policy tables, not one.** The brief sketched a single `reprocessing_domain_policies (tenant × domain × category)` carrying the serology rule. The serology rule is needed *before a category is known*: the late-reactive exposure handler sweeps a whole domain, and the dialysis isolation warning is evaluated per session, not per device. So the three serology fields live on `reprocessing_domain_settings (tenant × domain)` — the exact shape of `cath_reprocessing_settings` with a domain column — and `reprocessing_domain_policies (tenant × domain × category)` carries reprocessable / max cycles / cycle types / function check / TCV threshold, the exact shape of `cath_reprocessing_category_policies` plus two columns. Plan 2's admin and service code shapes carry over unchanged.
- **A third `reactive_patient_rule` value, `quarantine`.** Plan 2's `discard` means "the device is retired at post-use". Retiring a ₹2-lakh orthopaedic tray because it touched a reactive patient is not what any theatre does; the realistic action is to hold it for infection control, who either release it into a fresh cycle or discard it. Rather than make `discard` mean two things, the enum gains `quarantine`. Dialysis defaults to `discard` (a dialyser is a consumable), OT defaults to `quarantine`; either domain may choose either. The shared disposition function gains one branch; a parity test pins that, with no `quarantine` rule in play and **over the input domain the two functions share** (a non-null ceiling, a flag that equals "an active hold"), it answers exactly what cath's `computePostUseOptions` answers for the same inputs (§5.3).
- **`max_cycles` is optional, and its semantics are defined (review 2026-09-06).** Instrument sets have no meaningful cycle ceiling (wear is per instrument, which is not modelled); dialysers do. `max_cycles` is the maximum number of **reprocessing cycles (reuses)**, not of uses: `cycle_count` counts completed reprocessings, a device is usable while `cycle_count <= max_cycles`, and the ceiling is enforced at **reprocessing** — a `reprocessed` request at `cycle_count >= max_cycles` discards with `max_cycles_reached`, so the total number of uses is `max_cycles + 1`. With `max_cycles = 1`: use (cycle 0) → reprocess (cycle 1) → use (cycle 1, the one permitted reuse) → post-use discards. Capture never refuses on the ceiling alone (a device at `cycle_count = max_cycles` is on its last permitted use); `mintDeviceTx` refuses an `initial_cycle_count > max_cycles` and admits `= max_cycles` (one last use). `max_cycles_snapshot` is nullable, the bound CHECK reads `max_cycles_snapshot IS NULL OR cycle_count <= max_cycles_snapshot`, and **every ceiling comparison in the lane carries an explicit non-null guard** — the cath rule at `cathDeviceReuseService.js:141` reads `Number(device.cycle_count) >= Number(device.max_cycles_snapshot)`, and `Number(null)` is `0`, so an unguarded copy would treat every unbounded device as at its ceiling. §8 tests the full lifecycle at `max_cycles` 1, 2 and unlimited.
- **Historical exposure and an operational HOLD are two different records (review 2026-09-06, §5.5).** `exposure_flag` is history: set once, never cleared, read by lookbacks. A `reprocessable_device_holds` row is the restriction: placed by the late-reactive handler, a failed or invalidated load, a `serology_required` return, an inspection failure, a prion event or a person; resolved only by an authorised infection-control decision that records adjudication, the processing protocol required and the evidence. Issue-time and capture-time logic check **holds**, never the historical flag — which is what makes a released, reprocessed set re-issuable.
- **One release path (review 2026-09-06, §5.6).** Every transition to `available` goes through `releaseToAvailableTx`, which dispatches on domain: dialysis applies the release criteria on an approved protocol and writes the statutory row or an append-only attempt; OT requires the applicable processing event. The generic CSSD `reprocessed` command delegates to it and cannot bypass either. Deactivating a policy stops new enrolment and new processing; tracking, holds and settlement of existing devices continue.
- **An approved protocol is a precondition of reprocessability (review 2026-09-06, §4.2a).** A category becomes reprocessable only with a `reprocessing_protocols` row naming the approved basis (manufacturer IFU / guideline), its approver and its parameters — the TCV threshold (floor 80 %), the agent list with contact-time and concentration bounds, the residual-test requirement, the pathogen-specific reuse matrix and the surveillance interval. A catalogue of models is a follow-up; the reference is minimal now and required now.
- **Exposure delivery is durable (review 2026-09-06, §5.7).** The exposure event is written to `bloodborne_exposure_outbox` in the **same transaction** as the marker row; the post-commit handler call is the fast path and the reconciler applies holds idempotently for anything it missed. Required before stage-3 activation.
- **Three decisions, three functions (review 2026-09-06, point 5; §5.3).** *What evidence exists* is the resolver's `Decision` (Phase 1) or `resolveReuseStatus` (OT) — status, evidence kind, evidence date, surveillance currency. *Where a patient dialyses* is `computeIsolationWarnings` (§3.4), which reads `status` and maps the class to a bay. *Whether a device may be reprocessed for this patient* is `reuseEligibility` (§5.3), which reads the tenant protocol's pathogen-specific matrix, the surveillance currency, the device's active holds and the ceiling, and returns a verdict **code**. `computeDispositionOptions` consumes the third and never re-derives the first two. One `Decision.status` no longer carries three jobs.
- **End of use is a precondition of release (review 2026-09-06, point 8).** Nothing makes a device `available` while its patient-use episode is open: the dialysis reprocessing record requires the session to be `completed` (`actual_end_at` is set by `completeSession`) or `cancelled` from `in_progress` (aborted — `actual_start_at` set; the only two exits from a started session under `SESSION_TRANSITIONS`); an OT set is released only after its issue has reached `returned`. A record on an `in_progress` session is refused (`RPD_USE_NOT_ENDED`) — a **behaviour change** from `main`, where `recordReuseRegister` checks no session status (§5.1).
- **Dialysis has one category.** `reprocessing_domain_policies.category` for `dialysis` admits `dialyser` only (bloodlines are out of this release, §1.1); `procedure_pack` is admitted for OT so packs can be tracked, but a `reprocessable = true` row on it is refused by CHECK (§4.2).
- **OT sets get one register row each, linked 1:1 by `instrument_set_id`; `instrument_sets.status` keeps its nine values and the CSSD board keeps reading it.** The register row carries only what the set lacks (cycle count, ceiling, exposure, the six-state reuse status, the last passed load). The two states are kept coherent by four hooks inside `cssdService`'s existing transactions (§5.2) — issue, return, cancel, load transition — and a unit test pins that every `set_issue_log` write path in `cssdService.js` calls the hook. Where they can still disagree (a set edited by a path that does not exist yet) the register's row is the reuse truth and the set's row is the board truth; the device read joins both and exposes `set_status` beside `status`.
- **Dialysis isolation and the dialysis reuse decision consume one resolver, owned by the Phase 1 lane.** This lane writes nothing to `dialysis_patients.*_status`, keeps no sync, no latch and no union read of its own, and reads `resolveDialysisIsolation` (§3.3) for every isolation and post-use decision — live, never from the frozen snapshot. The derivation itself, its migration (767) and its backfill are dev-1b's; the Phase 2 census that gates the eventual DROP is this lane's.
- **The dialysis reprocessing record is one command.** `POST /sessions/:id/reuse-register` (existing) performs post-use and reprocessing together — the reuse room writes one form, and that is the form the statutory row is. Its body gains TCV, agent and contact time; the cycle count becomes read-only.

## 3. Serology gate

### 3.1 One resolver

`bloodborneMarkerService.resolveReuseStatus({ tenantId, patientUid, validityDays, asOf, db })` is already domain-free (it is patient-scoped and reads only `patient_bloodborne_markers`). **OT** calls it with the OT `serology_validity_days` from `reprocessing_domain_settings` (`instrument_sets` and `ot_schedules` carry no legacy serology). **Dialysis does not call it at all**: capture, the reprocessing record, the session read and the isolation rule read the Phase 1 resolver's `Decision` (§3.3), whose rule differs from this one on purpose — no validity window, and the retained roster columns as a legacy-declaration input. So "one resolver" is one *per record shape*: the cath resolver for cath and OT, the roster resolver for dialysis; neither lane re-implements the other's. The evidence-freezing rule from the cath spec §7.4 holds, with one sharpening stated in §3.3: `reuse_screen` (capture) and `post_use_screen` (return) on `reprocessable_device_usages` are evidence snapshots, written once and never an input to a later decision; every decision re-resolves live, and a later result changes the device through the exposure handler, never the historical rows. Both resolvers answer only *what evidence exists*; neither decides where a patient dialyses (§3.4) or whether a device may be reprocessed (§5.3) — the three decisions are separate functions (§2).

### 3.2 One exposure handler, two domain arms

`reprocessableDeviceService.quarantineDevicesExposedToPatient(event)` registers with `registerExposureHandler` at module load, exactly as `cathDeviceReuseService.js:1262` does. The registry is already domain-neutral; a second handler is a second `Set` member. For a reactive event `{ tenantId, patientUid, marker, testedOn, markerRowId }`:

- **dialysis arm** — every device whose `reprocessable_device_dialysis_links.dedicated_patient_uid` is the patient and whose status is not `discarded` (no window: a dedicated dialyser is that patient's for life, and the exposure is the patient's own history), plus any dialysis device with an open usage on that patient;
- **OT arm** — every OT device with a usage row for that patient with `captured_at >= tested_on − serology_validity_days` (Asia/Kolkata midnight boundary, the same `AT TIME ZONE` pin as 765), all uses for `cjd_suspected`. **`tested_on` may be NULL** once Phase 1's backfill writes legacy declarations (the hand-over note in §3.3 says NULL, never an invented date; `764:57` declares `tested_on DATE NOT NULL` today, so 767 relaxes it and this handler must not assume a value). A date-window comparison against NULL selects nothing, silently — the exact failure the owner named. **Decision: an undated declaration uses an unbounded lookback with infection-control review.** The predicate is `($3::date IS NULL OR u.captured_at >= …)`; every usage of that patient in the register is a candidate, each hold it places carries `reason_code = 'exposure_undated_declaration'`, and the IC notification says the evidence is undated. Justification: the register's own history bounds the sweep (usages exist only since this platform went live on the tenant, so "unbounded" is a few months, not a decade); a documented cutoff would have to be invented by the platform, which is the thing the hand-over note forbids; and a set used on a known carrier at any recorded time is at least worth an IC officer's look, which is what a hold is. The dialysis arm has no window in any case.
- each candidate is settled in its **own** transaction (the Plan 2 resilience contract: one lock timeout must not roll back nine quarantines), and **every write is marker-free** (D11(e), §2): `available` / `awaiting_reprocessing` / `in_cssd` → a **hold** (`placeHoldTx`, `hold_type = 'bloodborne_exposure'` or `'prion_exposure'` for `cjd_suspected`, `reason_code = 'exposure_late_result'` / `'exposure_undated_declaration'`, `source_marker_row_id = markerRowId`) plus the `quarantine` transition with `quarantine_reason = 'exposure_hold'` (a code, §4.3) and `exposure_flag = true`; `in_case` → the same hold row (status `active`, `pending_return = true`) and the flag, no transition — the hold is what the return path then reads (§5.2, §5.1); already `quarantined` → the event is associated with the existing hold when it represents a new source; replay of an already-applied event writes nothing because `bloodborne_exposure_applications` is unique per event × handler × device (§4.15). The hold itself is never used as the replay key; `discarded` re-checked under the lock and skipped. The device row, the usage row, the audit metadata (`rpd.device.exposure_flagged` carries `{ hold_id, hold_type, reason_code, status, domain }`) and the transition metadata **never name the marker**; the hold row's `source_marker_row_id` is the only pointer, and hold rows are readable only through the governance mount (§6.4) and the CSSD release dialog for the IC role (§6.2);
- **nothing is written to `dialysis_patients`** — the roster derives its state at read time through the Phase 1 resolver (§3.3), so the handler has no sync step;
- then one `cds_alerts` row (`alert_type = 'bloodborne_reuse_exposure'`, `severity = 'high'`, description naming the domain, the device tags and "a reactive blood-borne marker" — **not the marker**: `cds_alerts` is a patient-scoped table with readers outside the serology audience) and one `notification_outbox` row per active `INFECTION_CONTROL_OFFICER` (`type = 'bloodborne_reuse_exposure'`, `sourceEventKey = 'bloodborne-reuse-exposure:rpd:<markerRowId>:<officer uid>'`, body marker-free, deep link `/dashboard/cssd?tab=devices&domain=<domain>&hold=<id>` where the IC officer — an audience role — reads the hold and, through it, the marker row), raised for whatever subset settled even when others failed, and **idempotent under replay** (§5.7): the alert is skipped when a `cds_alerts` row with the same `source_data.marker_row_id` already exists, and the notification's `sourceEventKey` already deduplicates. The existing notification channel is `notificationOutbox.queue` (`utils/notifications/notificationOutbox.js`), exactly as `cathDeviceReuseService.quarantineDevicesExposedToPatient` uses it on `main`.
- **Handler registration is explicit.** `exposureHandlerBootstrap.js` (#1016, on `main`) imports `cathDeviceReuseService.js` for its side effect and states that a new handler owner is added there; this lane adds `import './reprocessableDeviceService.js';` to it, and `exposureHandlerCount()` is asserted to be **2** in the platform's own unit test and in the reconciliation script's pre-flight (`reconcile-bloodborne-markers.mjs` refuses `--apply` at zero; it now also prints the count and the plan expects 2).

**Durable delivery (review 2026-09-06, §5.7).** The crash window between the marker commit and the handler call is no longer a notification problem: patient A's set is used, the reactive result commits, the process dies before the handler runs, and patient B — clear — is assessed later; re-resolving B cannot discover A's missed exposure, because the missing information is the device's hold. So the exposure event is written to **`bloodborne_exposure_outbox` in the same transaction as the marker row** (`enqueueExposureEventsTx`, called by `bloodborneMarkerService.recordMarkers` and `recordMarkersFromSignedResults` inside their `setTenantTx` before commit — the two writers on `main` that call `notifyExposureHandlers` post-commit), the post-commit fan-out is only a fast claim of durable handler work. It records explicit handler/device/notification results and may mark an event complete only when every stable handler id reports zero remaining obligations; a reconciler re-drives incomplete work idempotently. It is a table of its own, modelled on `event_outbox`'s lease / backoff / dead-letter shape (mig 588) rather than written to it — `event_outbox`'s only consumer is the webhook fan-out (`completeClaimedEventFanout` writes `webhook_deliveries`), so a row there would be claimed by the wrong consumer and marked delivered with nothing done. The design is in §5.7; it is a precondition of stage-3 activation (§1.2).

### 3.3 Isolation derivation — dependency on the derivation lane

**What changed and why.** The first draft of this section derived `dialysis_patients.hbsag_status / hcv_status / hiv_status` from the marker record inside this lane: a service-side sync with a no-downgrade latch, a union read of the two records during transition, a `dialysis_surveillance` marker source, an enrol-body guard and a one-shot backfill script. That collided head-on with the **dialysis isolation derivation lane** (dev-1b), which owns the same three columns, the same enrolment default and the same roster surfaces. A decision trio (advocate / challenger / supervisor, 2026-09-05) ruled **two-phase**, and this document now treats the carve as settled: Phase 1 owns derivation, resolver and migration 767; Plan 4 consumes the resolver and owns the Phase 2 census.

**Phase 1 — the derivation lane (dev-1b; migration 767).** Not built here; stated so this lane's dependency is explicit:

- A **read-time resolver is the only input to any isolation decision**. The three `dialysis_patients.*_status` columns are **retained, read-only**, as legacy-declaration inputs to a union read inside the resolver. There is **no sync write** onto them and **no no-downgrade latch**: a column is a declaration made by a person on a date, and the resolver weighs it as one input beside the marker rows.
- The isolation rule is **distinct from `computeReuseStatus`** (the cath resolver): a non-voided reactive marker → `restricted`; any non-voided non-reactive → `clear` **regardless of age**; nothing → `unknown`. The cath rule's 90-day `clear` window is wrong for a roster: with zero markers cluster-wide today, a window would leave every marker-less roster `unknown` forever. **The legacy-column arm is asymmetric (Q1 as revised, below):** a `'positive'` column restricts on its own; a `'negative'` column is not evidence of anything.
- `unknown` **never isolates and never blocks**. Enrolment writes `'unknown'`, not `'negative'` (the `'negative'` default was a claim nobody made). Amber renders as a **roster chip only**; no per-session warning fires for it — `DIALYSIS_SEROLOGY_UNKNOWN` **does not exist** (§3.4). Unknown-isolates would isolate every patient on day one.
- Invariant (d): a voided reactive with **no other evidence** falls back to the **column**, not to `clear` — a void un-isolates only when the marker was the sole evidence.

Revision 2 found that the v1 shape cannot support protocol-specific surveillance, device-pinned evidence, or safe cohort compatibility. Stage 2 for Plan 4 therefore requires the Phase 1 owner to accept and publish this versioned extension; until then the dialysis adapter fails closed with `RPD_ISOLATION_CONTRACT_VERSION_UNSUPPORTED`. - A thin single-uid wrapper exists for the per-session paths; this lane binds to both through one adapter (`dialysisReuseService.isolationDecisionTx`), so a Phase 1 rename is a one-line change here.
- **No boolean pair.** `{ isolated, unknown }` admits an illegal fourth state; `status` is the one field.
- **Marker detail is opt-in and default off**, so a caller that forgets gets the safe shape. **No caller in this lane passes `includeMarkers: true`.** The one surface that may — the roster / patient-detail read behind `roleSeesSerologyDetail` — is Phase 1's roster work; this lane does not attach a resolver call to the existing `GET /patients/:id` (an existing read must not start answering 503 on a build without Phase 1). The adapter carries the flag so that surface has one seam to use; the session evaluator (`assessIsolationTx`), capture, the reprocessing record, the session read and the CSSD paths never forward it.
- **`isolation_class` is opt-in on the same footing as marker detail, and this lane's ask is settled that way.** Plan 4 first asked for it as an unconditional fifth field. dev-1b refused, and was right: a value of `'hiv'` **is** serology whatever the caller calls it, and "it is a routing instruction, not a marker value" is the same reframing that produced the two earlier disclosures this canary exists to catch. So the field is **present only when `includeIsolationClass: true`**, and **`null` unless `status === 'restricted'`** — a caller that forgets gets the safe shape, exactly as with `includeMarkers`. Phase 1 computes it from the rule this lane hands over: one reactive core marker → its class; two or more → `isolation_mixed`; `restricted` for a marker with no machine class (`cjd_suspected`, other) → `isolation_mixed`; not restricted → `null`.
- **Who may pass `includeIsolationClass: true`.** Under D11 = NO, **exactly two** server-side paths (review 2026-09-06 raised this from one): the **session-evaluation path** — `assessIsolationTx`, which does the read, and `evaluateIsolationForSessionTx`, which wraps it for start and reassign (§3.4) — where the class is mapped to the tenant's routing group through `reprocessing_domain_settings.isolation_groups` (§4.1); and the **reuse-eligibility path** — `reuseEligibilityTx`, called by the dialysis post-use record (§5.1) and by the OT return hook for an OT patient's `Decision`-shaped restriction only when the tenant protocol's matrix is pathogen-specific (§5.3) — where the class indexes the protocol's reuse matrix (HBsAg-reactive → no reuse; HIV-reactive → no reuse; HCV per protocol). Both are in-process decisions: the class is **never rendered, never serialised, never snapshotted and never audited** by either; what leaves each frame is a group label or an eligibility verdict code. The roster, the today board, the case / session lists, patient detail, capture, the session read and every CSSD path **never pass it**, so their `Decision` has no `isolation_class` key at all. The plan pins the asker count at **two, by function name** (§8).
- **Null-class semantics are defined per status and per flag (review 2026-09-06, point 7).** With `includeIsolationClass: true`: `status = 'restricted'` **requires** a class in the four-value set (absent or `null` → `RPD_ISOLATION_DECISION_INVALID`); `status = 'clear'` or `'unknown'` **requires `null`** (a non-null class on a non-restricted Decision is a resolver defect → `RPD_ISOLATION_DECISION_INVALID`). With the flag **off**: the key is normally **absent** and that is the valid shape; a key that is *present* is tolerated only when `null`, and a present non-null class the caller never asked for is refused too — an unrequested class is exactly the disclosure the opt-in contract exists to prevent, and failing closed there costs nothing. §8 tests all three statuses under both flag settings; the adapter's `assertDecisionShape(decision, askedForClass)` is the one place the rule lives.
- **The adapter's fail-closed check keys on the ask, not on presence.** `RPD_ISOLATION_DECISION_INVALID` (500) fires on the table above — a real invariant, because a wrong shape must not route a patient or admit a dialyser to reuse. Asserting presence unconditionally would only re-create the rejected contract inside our own code.

**Q1 as revised — the legacy columns are ASYMMETRIC evidence (owner, 2026-09-06, via dev-1b; INPUT to the Phase 1 lane's contract, which owns migration 767 and this rule; #1014 consumes it and says so).** Q1 was first answered on 2026-09-06 as "a legacy `'negative'` means `clear`" and **revised the same day** once the schema fact was in front of the owner: `168` declares each column `DEFAULT 'negative'` and `enrolPatient` writes `COALESCE($8, 'negative'), COALESCE($9, 'negative'), COALESCE($10, 'negative')` when serology is omitted, so a bare `'negative'` is indistinguishable from *nobody having said anything*, and the literal rule would have resolved every never-tested patient as `clear` — fail-open on blood-borne isolation. The precise rule, written here exactly as dev-1b stated it so the next reader cannot soften it:

- a legacy **`'positive'`** contributes **`restricted` on its own**, with no corroboration required — it is never the default and is written only by explicit enrolment input or by `recordSerology`'s promotion `UPDATE` (`dialysisService.js` ≈1160-1170), so it has provenance. Applying a corroboration requirement to this arm would **un-isolate declared positives** — also fail-open — which is why the rule is asymmetric rather than a symmetric "corroborate both";
- a legacy **`'negative'`** contributes **nothing**. It is **not an input to `clear`** — not a weaker clear, not an AND with corroborating evidence: when a `dialysis_serology` row or a `patient_bloodborne_markers` row exists for the analyte, **that evidence decides by itself** and the column never changes an outcome. Write it as "the negative column is not evidence", never as "negative + evidence = clear" — an AND keeps a meaningless column load-bearing, and the next reader will not know it is inert;
- only a `'negative'` column and **no** marker row and **no** `dialysis_serology` row for the analyte → **`unknown`**;
- invariant (d) is intact and is a **positive** fallback: a voided reactive with no other evidence falls back to the column, which can only re-restrict (a `'positive'`) and can never clear.

**Per-marker semantics** (an input to Phase 1, so the roster rule matches `computeReuseStatus` on this one point while keeping its window-less semantics — `bloodborneMarkerRules.js`, `CORE_MARKERS.every(...)`): `clear` requires **each of the three core analytes** to be cleared by a non-voided non-reactive `patient_bloodborne_markers` row or a non-reactive `dialysis_serology` value (`hbsag`, `anti_hcv`, `hiv`; `168`); one cleared analyte never clears an untested one. A `dialysis_serology` row is human-entered, dated (`test_date`), attributed (`reported_by`), and since #1024 stamped with its own tenant. The legacy negative is not what corroborates that result: the evidence row decides by itself. `evidence: 'legacy_declaration'` therefore arises only from a **positive** roster column; a negative-only roster value with no evidence row remains `evidence: 'none'` and resolves `unknown`.

**Evidence date and surveillance currency stay separate from cohort status.** The `Decision` gains `evidence_dated_on` (the latest per-analyte date; `null` when any deciding evidence is undated) and `surveillance_overdue: boolean` against the tenant protocol's surveillance interval (`168`'s header states baseline plus three-monthly HBsAg/HCV and annual HIV; the interval is configured on the protocol, §4.2a). Routing reads `status` alone. Reuse eligibility (§5.3) reads `surveillance_overdue` and treats overdue evidence as unknown for reprocessing when the protocol says so (default `true`). Neither decision reads a legacy negative. Pre-#1024 `dialysis_serology` rows can carry the default tenant id, so migration 767 must either repair that tenant stamp or resolve them through the in-tenant `dialysis_patient_id`; and `dialysis_serology` admits both `'positive'` and `'reactive'` while `recordSerology` promotes only `'positive'`. `dialysis_patients` has no `updated_by`, so the roster row cannot prove provenance.

**Consequences for this lane:** day-one amber is higher than the literal Q1 predicted — every roster row whose three columns are only the enrolment default resolves `unknown` — and under `unknown_serology_rule = 'warn'` each such patient's first dialyser reprocessing needs an acknowledgement. The census in §7.6 reports declared-and-evidence-backed negative observations separately from defaulted negative-shaped roster values. Because today's roster schema cannot distinguish a deliberately entered `'negative'` from its default, the honest column-only declared-negative count is **zero** unless a serology row backs the observation; a large number is a census bug, not a finding.

**Snapshot versus decision** (dev-1b's fourth point). `reuse_screen`, frozen on the usage row at dialyser capture, is an **evidence snapshot**: "what was known when this dialyser was captured". It is written once, is never re-read as current state, and is never an input to any decision. Both decisions this lane makes for dialysis **re-resolve live** through the resolver: schedule / start / reassign machine routing (§3.4) and the post-use reprocess / quarantine / discard decision (§5.1). The snapshot exists so an audit can see what the capturing user saw; a marker recorded between capture and start must reach the machine assignment, and one recorded between capture and the reprocessing record must reach the disposition. `post_use_screen` is the same kind of object: the `Decision` the reprocessing record acted on, frozen after the fact. **Neither snapshot carries marker detail or `isolation_class`**. `assessIsolationTx` consumes the class for class-to-group routing and `reuseEligibilityTx` consumes it for the server-side matrix before any response or snapshot is built; the adapter's `snapshotOf` has no `keepClass` form. ### 3.4 The dialysis isolation WARN rule

Evaluated in `startSession` and `scheduleSession` (both existing) for the session's machine and patient, and re-evaluated by `PATCH /sessions/:id/machine` (new, §6.1). Every evaluation reads a **live `Decision`** from the Phase 1 resolver (§3.3) — never the frozen `reuse_screen` — so a marker recorded between capture and start reaches the machine assignment. **DEPENDS ON Phase 1.** In `scheduleSession` the evaluation runs **before** the `INSERT`, inside one `setTenantTx` (today's `scheduleSession` inserts with the bare client outside any transaction — `dialysisService.js:466-481` — so a `block` refusal raised after the insert would leave an orphan `scheduled` row): `assessIsolationTx` reads and decides without writing, the `INSERT` itself carries the isolation columns, and a `DIALYSIS_ISOLATION_MACHINE_BLOCKED` at scheduling leaves no row (a deep test asserts the count). `startSession` and the reassign route call `evaluateIsolationForSessionTx`, which is `assessIsolationTx` plus the `UPDATE` onto the existing row. Pure function `computeIsolationWarnings({ decision, machine, isolationGroups, enforcement })` — `isolationGroups` is the tenant’s class → group map from `reprocessing_domain_settings` (§4.1), so the mapping is data the caller supplies and never a table the rules module owns:

| Condition | Code | Severity under `warn` | Under `block` (review 2026-09-06: no escapes) |
|---|---|---|---|
| decision `restricted` and no `dialysis_machines` row for `machine_no` | `DIALYSIS_MACHINE_UNREGISTERED` | warn | **block** — a restricted patient cannot be started on a machine the unit has not registered |
| decision `restricted`, machine registered, machine's `isolation_group` does not satisfy the patient's `required_group` (rule below) | `DIALYSIS_ISOLATION_MACHINE_MISMATCH` (the marker class stays server-side; the payload names the **group**) | warn | block |
| decision `restricted`, the tenant has **not mapped** the class (`required_group` null) | `DIALYSIS_ISOLATION_GROUP_UNMAPPED` (new) | warn — any non-null group satisfies, as before | **block** — an unmapped class is a refusal; block mode is not entered with an incomplete map (precondition below) |
| decision `unknown` | no marker-derived warning on a general machine; `DIALYSIS_UNKNOWN_ON_DEDICATED_GROUP` if a dedicated group is selected | warn and require acknowledgement | **block** unless a bound emergency authorisation is supplied — unknown is not proof of HBV-cohort compatibility |
| decision `clear`, machine registered, `isolation_group IS NOT NULL` | `DIALYSIS_GENERAL_PATIENT_ON_ISOLATION_MACHINE` | warn | warn |

A clear patient on an unregistered machine produces nothing — otherwise every session on day one warns, and a warning nobody reads is not a warning; an `unknown` patient produces no marker-derived warning but is **not cohort-compatible with an HBsAg-dedicated group**. It may use a general machine under standard precautions; selecting any dedicated group requires the explicit emergency authorisation below. Unknown therefore never becomes evidence of compatibility. **The required group** is `settings.isolation_groups[Decision.isolation_class]`: Phase 1 computes the class by the rule handed over in §3.3 (`hbsag → hbsag`, `hcv → hcv`, `hiv → hiv`; two reactive markers → `isolation_mixed`), and this lane maps it to the tenant's own label server-side, deriving neither from markers. **Satisfaction rule:** a machine with `isolation_group IS NULL` is a general machine and never satisfies a restricted patient; when the tenant has mapped the class the two labels must be equal; when it has **not** (`required_group` is `null` — the day-one state) any non-null group satisfies **under `warn` only**, because the patient is at least on an isolation machine and the platform must not invent a bay name. Before that label is produced, `cohortCompatibilityTx` compares the full protected infection profiles: HBsAg-positive cohorts are compatible only with the same HBsAg status, and HCV/HIV combinations cannot be collapsed into HBV equivalence. Two classes may share a human-facing label only when the compatibility matrix proves the profiles safe; `isolation_mixed` is not itself a compatibility class (§4.1). When the code list is non-empty, `startSession` requires `isolation_override_reason` (400 `DIALYSIS_ISOLATION_OVERRIDE_REQUIRED`) and records it with actor and time; under `block`, `UNREGISTERED`, `MISMATCH` and `UNMAPPED` all refuse with 409 `DIALYSIS_ISOLATION_MACHINE_BLOCKED` (carrying `codes`) regardless of reason. The codes, the required group, the mode pair and the override are persisted on `dialysis_sessions` (§4.7) and audited as `dialysis.session.isolation_overridden`.

**Preconditions for `block` (review 2026-09-06).** `PUT /domains/dialysis/settings` with `isolation_enforcement = 'block'` is refused with 409 `RPD_ISOLATION_BLOCK_PRECONDITIONS` (carrying `unmapped_classes[]`, `groups_on_no_active_machine[]`, `active_machines`) unless: every one of the four classes is mapped; every mapped group is carried by at least one **active** `dialysis_machines` row; and the tenant has at least one active machine. Every assessment also rejects the **selected** machine when it is inactive; another active machine in the group cannot validate a retired selection. A later machine retirement or a mapping edit that would break these while `block` is on is refused with the same code.

**Emergency exception — explicit, bound, expiring, and one-use.** Because a session id does not exist before scheduling, `POST /api/v1/dialysis/isolation-emergency-authorizations` accepts `{ patient_uid, proposed_machine_id, scheduled_for, reason }` under `DIALYSIS_EMERGENCY_OVERRIDE_ROUTE_ROLES`. It records the patient, selected active machine id and version, the v2 Decision/evidence fingerprint, settings/policy/protocol revision ids, creator, purpose, and `expires_at` (maximum four hours). `scheduleSession` in block mode may consume that authorisation to create the booking; `startSession` locks and revalidates every binding, refuses changed evidence/policy/machine or expiry, rechecks device admission, and consumes it exactly once in the same transaction that starts use. Machine reassignment always invalidates it. The session-id endpoint may create the same bound record for an existing non-startable booking; it is not a timeless boolean on the session. Both paths write `medication_safety_reviews`, audit the authorisation and consumption, and notify infection control. A dialysis technician cannot invoke them.

**The user-facing payload (D11 = NO, §2).** `computeIsolationWarnings` returns `{ codes, required_group, blocked }`. The marker class is an **internal intermediate only**: a local inside that function, read off the live `Decision` to index `settings.isolation_groups`, and a key of nothing — not the return value, not the internal isolation object, not an audit row, not a response. What the API emits:

```
isolation: {
  codes:              ['DIALYSIS_ISOLATION_MACHINE_MISMATCH', …],       // the persisted flat list
  isolation_warnings: [{ code, machine_id, severity, required_group }], // one entry per code; GROUP, never class
  warn_only, enforcement_enabled, override
}
```

`machine_id` is the `dialysis_machines.id` the warning is about and is `null` for `DIALYSIS_MACHINE_UNREGISTERED`; `severity` is `'warn'` or `'block'` from the table above; `required_group` is the tenant's label for the bay this patient belongs in, and is `null` when the patient is not restricted or the tenant has not mapped the class. The `DIALYSIS_ISOLATION_MACHINE_BLOCKED` 409 carries `{ codes, required_group }` and names the group in its message ("… must be dialysed on a machine in isolation group Bay 1", degrading to "… on an isolation machine" when `required_group` is `null`). `required_class` **does not exist** on any of these. `DialysisIsolation`'s OpenAPI schema is `additionalProperties: false` (§6.6) and lists `required_group` and never a class, so a payload that starts carrying a class fails schema validation before it reaches a reviewer — the shape is enforced, not merely documented.

### 3.5 Projection for non-audience roles

`DIALYSIS_ROUTE_ROLES` admits three roles outside `roleSeesSerologyDetail` (`CLINICAL_STAFF_ROUTE_ROLES`): `BLOOD_BANK_TECHNICIAN`, `BLOOD_BANK_STAFF` and **`DIALYSIS_TECHNICIAN`**. `CSSD_ROUTE_ROLES` admits six (`STORES_PURCHASE_INCHARGE`, `HR_STAFF`, `QUALITY_OFFICER`, `INFECTION_CONTROL_OFFICER`, `DATA_PROTECTION_OFFICER`, `COMPLIANCE_OFFICER`). `THEATRE_ROUTE_ROLES` admits none. Every read surface added or changed by this lane projects by role through the **same predicate** (`cathDeviceReuseService.roleSeesSerologyDetail`, deliberately not a second list), keys blanked never dropped:

- `reuse_restriction` on every payload: `projectReuseRestrictionForRole` (existing) — for OT the cath shape: `status`, `validity_days`, `evaluated_at` survive; `reasons` and `markers` empty. For dialysis the payload is the resolver's `Decision` (§3.3): `status`, `asOf`, `evidence` survive; `reasons` emptied; `isolation_class` **blanked to `null`** for a non-audience role (keys blanked, never dropped) — belt and braces, because no read surface in this lane passes `includeIsolationClass`, so the key is absent on these payloads to begin with. `markers` is never present on these surfaces (no caller in this lane forwards `includeMarkers`; the projection drops the key anyway, and the canary's poisoned Decision carries one so a forwarding route fails).
- **The frozen `reuse_screen` and `post_use_screen` are sanitised ON RESPONSE (review 2026-09-06, point 1).** They are stored complete — `reasons` included, because the audit purpose of a snapshot is to show what the capturing user saw — but they are **never returned raw**. Every surface that returns a usage row (`GET /sessions/:id/dialyser`, the capture response, `GET /reprocessing/devices/:id/history`, the theatre sets read) passes the usage through `projectUsageForRole(usage, role)`, which applies `sanitizeScreenForRole` to both screens: for a non-audience role `markers` is dropped, `isolation_class` is blanked to `null`, and **`reasons` is emptied** — removing the marker keys does not make free text like "HBsAg reactive 2026-08-12" safe. For an audience role the screens pass unchanged. The `ReprocessableDeviceUsage` schema declares both screens as `DialysisIsolationDecision`-or-`BloodborneReuseStatus` shapes with `additionalProperties: false`, and the canary poisons the stored screen's `reasons` with the sentinel so an unprojected usage fails (§3.6). A usage row is therefore the fourth projected object beside the restriction, the roster row and the serology row, through the same predicate.
- `isolation` / `isolation_warnings[]`: **still not projected — because there is nothing in them to project.** `codes`, `machine_id`, `severity` and `required_group` reach every dialysis role: whoever puts the patient on a machine must know that a warning fired, which machine it is about and which bay the patient belongs in. `required_group` is a tenant's label for a room, not a clinical value — that is the whole point of D11 = NO — while the marker class does not reach them and does not exist in the payload at all (§3.4). Review round 1's Fix-6 — "do not blank `required_class`; it is a routing instruction, and blanking protects nothing because `GET /machines` publishes every machine's class and the two mismatch codes narrow it by elimination in at most three attempts" — is **SUPERSEDED** by D11: the recoverability argument was a reason to relabel the machine layer, which is what the owner chose, and not a reason to publish the class outright; the same "it is a routing instruction, not a marker value" reframing is what dev-1b rejected on the resolver contract. Under the relabel that elimination recovers a bay name and stops there. The canary pins the *value*, not the key (§3.6).
- `dialysis_patients` rows on roster, today board and patient detail: `hbsag_status`, `hcv_status`, `hiv_status` → `null`; `isolation_required` survives (the advisory). `dialysis_serology` rows in patient detail: `hbsag`, `hbs_titre`, `anti_hcv`, `hcv_pcr`, `hiv` → `null`, `is_seroconversion` → `false`; `test_date` survives.
- The CSSD queue carries no patient identity and therefore nothing to project; the canary proves it (§3.6).

**D10 consequence (decided per role; D11 is also decided).** The dialysis technician sees the restriction status, isolation codes, machine, and required **group** — enough to route — but not marker values, reasons, lab rows, or a marker class. D10a/b/c are each NO in this lane (§2): neither the technician nor either blood-bank role joins the serology-detail audience. The actual-assignment census still runs because provisioning policy cannot prove that no account already holds a role. A future audience widening would be a separate reviewed change and would not put a class into a routing payload.

**Revision 2 hold/evidence boundary.** `projectHoldForOperationalRole` is an allow-list, not a blacklist: CSSD/device readers receive only `{ id, device_id, operational_type, reason_code, status, pending_return, processing_required, created_at }`. It omits notes, adjudication, evidence documents, source references, patient/case ids, and nested metadata. Exact marker evidence is available only from `GET /api/v1/reprocessing/holds/:id/evidence` under `HOLD_EVIDENCE_REVIEW_ROUTE_ROLES = {INFECTION_CONTROL_OFFICER, CONSULTANT, ADMIN, SUPER_ADMIN}`, with tenant/purpose checks and a HIPAA access log. This is a narrow, purpose-bound evidence-review authority and does not add `INFECTION_CONTROL_OFFICER` or any D10 role to the platform-wide serology-detail audience. D11 governs marker-neutral routing payloads. Prion/CJD is a different hazard boundary: operational CSSD payloads say `specialist_contamination_hold`; the exact `prion_exposure` category and evidence appear only on the authorised evidence/investigation surface and never become a dialysis routing class.

### 3.6 The canary gains four mounts

`serologyDisclosureCanary.test.js` enumerates exactly three mounts today (`/api/v1/cath-lab`, `/api/v1/stemi-pathway`, `/api/v1/cath-reprocessing`). The disclosure predicate gains **three** checks beside the existing ones: any object carrying a non-null `hbsag_status` / `hcv_status` / `hiv_status` (or a non-null `hbsag` / `anti_hcv` / `hiv` / `hbs_titre` / `hcv_pcr`, or `is_seroconversion === true`); any `reuse_restriction` (or `restriction`) with a non-empty `reasons` or `markers`; and — the D11 sentinel — any node carrying an `isolation_class` or `required_class` whose **value** is one of `hbsag` / `hcv` / `hiv` / `isolation_mixed`. The third mirrors the existing `critical_items` check exactly: a **value** test against a named set (`SEROLOGY_CODES` plus `isolation_mixed`), not a key-presence test, so the key may be absent or `null` and only a marker-class string fails. It carries the same shape guard `serologyItemLeaks` uses: a node with a `machine_no` is a `dialysis_machines` row. Its `isolation_group` is *equipment* data that `GET /machines` publishes to every dialysis role — a bay label, not a marker class — so it is not in the value set and could not trip the sentinel even without the guard; say so rather than deleting the guard, which **stays** to keep a future machine column (or a fixture that revives `isolation_class` on a machine row) from being read as a patient's class. ## 4. Data model

All new tables: `tenant_id UUID NOT NULL` with the GUC default used by 765, `REFERENCES tenants(id) ON DELETE CASCADE`, `ENABLE` and `FORCE ROW LEVEL SECURITY`, the `tenant_isolation` policy verbatim from 765, a role-guarded GRANT block (SELECT, INSERT, UPDATE; DELETE and TRUNCATE revoked; sequence USAGE and SELECT only), registration in `src/lib/prisma.js`'s `runtime_mutable_no_delete_relations` and `runtime_nextval_sequences`, `prismaCoverage.test.js` pins, and `TABLE_COLUMN_SEED_OVERRIDES` entries. Every CHECK is named. Every FK into an existing table is a tenant-pinned composite; composite `SET NULL` actions carry the column list. Only the two patient-keyed FKs are `DEFERRABLE INITIALLY DEFERRED` (the patient-merge sweep re-points `patient_uid` under `SET CONSTRAINTS ALL DEFERRED`). No relation fields are added to `schema.prisma` for the new FKs (`check:prisma-relations` budget); the mirror carries scalars, uniques and indexes only.

None of the **seventeen** Plan 4 relations (§4.1–§4.6, §4.12–§4.16) is baseline-owned. Mutable workflow/queue relations are registered as no-delete; physical occurrences, revisions, attempts, hold satisfactions, exposure applications and operation receipts are append-only with SELECT + INSERT only. Existing baseline-owned tables are ALTER-only, so the census manifest and `expectedAbsentCount` (411) do not change. `dialysis_patients` is untouched. The only Phase 1 schema dependency is the requested `(tenant_id, id)` parent unique on `patient_bloodborne_markers`; Plan 4 must not fall back to single-column marker FKs because referential-integrity checks bypass RLS.

### 4.11 Migration `NNN` outline and the 753/758 hazard

`NNN_reprocessable_devices_platform.sql` (`NNN` = the next free migration number at implementation push time; 767 remains reserved for Phase 1) is one additive transaction with `lock_timeout 5s` / `statement_timeout 300s`. It creates **seventeen** Plan 4 relations: the original settings, policy, protocol, register, usage, dialysis-link, machine, hold, processing-event, attempt, and exposure-outbox relations, plus `reprocessing_protocol_device_scopes`, `device_processing_event_revisions`, `reprocessable_hold_satisfactions`, `bloodborne_exposure_deliveries`, `bloodborne_exposure_applications`, and `reprocessable_device_operations`. The dependency order is: backing tenant-pinned uniques; protocols and protocol-device scopes; settings and policies; devices and usages without cyclic FKs; processing events, revisions, holds, satisfactions, attempts and operations with their deferred reverse FKs; links and machines; exposure outbox, deliveries and applications; existing-table additive columns/constraints; then RLS, sequences, immutable triggers and grants. The exact mutable-versus-append-only registry and grant lists are pinned by `prismaCoverage.test.js`: event occurrences, event revisions, attempts, hold satisfactions, exposure applications and operation receipts are INSERT-only; queue/delivery state is mutable but DELETE/TRUNCATE-revoked.

The Phase 1 amendment, not `NNN`, adds `UNIQUE (tenant_id, id)` to `patient_bloodborne_markers`; both marker FKs are blocked until that v2 parent key exists. The migration header states the domain split, immutable protocol revisions, device applicability, obligation-based availability, marker-free register, and that neither `dialysis_patients`, `patient_bloodborne_markers`, nor `cath_reprocessable_devices` is otherwise changed. Baseline-owned relations remain ALTER-only, so the inline-check census manifest and `expectedAbsentCount` remain unchanged.

**753/758 hazard assessment.** `cath_inventory_authority_assert_contract_753(uuid, bigint)` is bound to `cath_case_consumable_usage` and names `public.cath_reprocessable_devices` directly in its `reused_device` branch (765:551); `cath_authority_identity_guard_753()` dispatches on `TG_TABLE_NAME` over `cath_lab_cases`, `cath_consumable_catalog`, `cath_case_consumable_usage`, `tasks`, `workflow_sla_instances`, `notification_outbox` and `pharmacy_stock_movements`. None of the tables `NNN` creates or alters is on either list, and `NNN` does not insert into any of them. **Confirmed: a new generic table trips neither assert, and no plpgsql body is re-declared by this migration.** The scouting brief's conclusion stands.

## 5. Flows

### 5.1 Dialysis

**Capture** — `POST /api/v1/dialysis/sessions/:id/dialyser`, idempotency scope `dialysis_dialyser_capture`, session guard before the claim. Body `{ manufacturer_serial?, device_tag?, model_name?, manufacturer?, hospital_asset_id?, baseline_tcv_ml?, initial_cycle_count?, exposure_acknowledgement?: { reason } }` — exactly one of `manufacturer_serial` / `device_tag`. Inside one tenant transaction, session locked `FOR UPDATE`:

1. Session status ∈ {`scheduled`, `in_progress`}, no open usage on the session → else 409 `DIALYSER_ALREADY_CAPTURED`. The `dialyser` category policy must be reprocessable → else 409 `RPD_POLICY_NOT_REPROCESSABLE` (dark by default: the capture route refuses until a policy exists, and the legacy free-text `dialyser` column keeps working as today).
2. Resolve the device `FOR UPDATE` by tag, or by `(tenant, 'dialysis', manufacturer_serial)`; a serial nobody has seen mints a row (`enrolled_via = 'session_capture'`, `status = 'available'`, `cycle_count = initial_cycle_count ?? 0` with `metadata.enrolled_mid_life = true` when non-zero, `max_cycles_snapshot` from policy) and a link row dedicated to the session's patient with `baseline_tcv_ml` if given. A tag unknown in the tenant → 404 `RPD_DEVICE_NOT_FOUND`; a tag whose device is not `dialysis` → 409 `RPD_DOMAIN_MISMATCH`.
3. **Dedication**: link row exists and `dedicated_patient_uid <> session patient` → 409 `DIALYSER_DEDICATED_TO_ANOTHER_PATIENT`. No override exists for this; a dedicated dialyser on another patient is a never event.
4. Device status must be `available` → else 409 `RPD_DEVICE_NOT_AVAILABLE` with the status. **No active hold** on the device → else 409 `RPD_HOLD_ACTIVE` (§5.5; the historical `exposure_flag` is never a capture-time input). The ceiling **never refuses a capture**: a device at `cycle_count = max_cycles_snapshot` is on its last permitted use (§2, `max_cycles` semantics); `RPD_MAX_CYCLES_REACHED` is a reprocessing-time and mint-time refusal only. **Residual test (review 2026-09-06, point 6):** when the device's `residual_test_pending` is set (a reprocessed dialyser under a protocol with `residual_test_required`), the body must carry `pre_use_residual_test: 'negative'` → else 409 `RPD_RESIDUAL_TEST_REQUIRED`; the value is written on the usage and the device flag cleared in the same statement. A deactivated policy (§4.2) refuses (`RPD_POLICY_DEACTIVATED`).
5. The resolver's live v2 `Decision` is frozen as `reuse_screen`. Capture is a **reservation**, not authority to begin physical use. `deviceEligibilityTx({ action: 'use' })` checks whether the already-prepared device may be used; it deliberately does not apply the reprocessing-cycle ceiling, so `cycle_count == max_cycles` remains the last permitted use. `deviceEligibilityTx({ action: 'reprocess' })` applies the ceiling and protocol matrix to a proposed new processing cycle. The action is mandatory—there is no default—so the two questions cannot be conflated. The actual-use boundary repeats the `use` check after all locks (§5.3). Matrix no-reuse remains unacknowledgeable; HCV dedicated reuse remains the only pathogen-specific reuse branch.
6. Write the usage row (`dialysis_session_id`, `patient_uid` — read from the locked session's roster row, never the body — `reuse_cycle = device.cycle_count`, `capture_source`, `capture_provenance = 'live'`, `ready_processing_event_id = device.last_processing_event_id`, `pre_use_residual_test`), device → `in_case` (`version + 1`), `dialysis_sessions.dialyser = COALESCE(model_name, manufacturer_serial)` and `reuse_count = reuse_cycle` (the legacy columns become derived, so the today board and the completion billing path keep working unchanged). Audit `rpd.device.captured`; realtime `dialyser-captured`; the response carries the command receipt (§5.8).

**Actual-use admission.** `startSession`, inside its session transaction and before `actual_start_at`, acquires the patient advisory lock, reconciles or refuses all committed exposure work relevant to the captured device, locks device/usage/holds/readiness, verifies dedication, active policy/protocol revision, still-valid processing evidence, residual attestation for this episode, `deviceEligibilityTx({ action: 'use' })`, selected-machine activity and cohort compatibility, then evaluates isolation. A hold or invalidation arriving after capture therefore refuses start. `scheduleSession` remains planning only; it never substitutes for this admission boundary.

**Reprocessing record** — `POST /api/v1/dialysis/sessions/:id/reuse-register` (existing route; now claims a key: scope `dialysis_reuse_register`, `retainOnServerError: true` because a per-session upsert has no self-blocking `from` list — scouting risk 8). Body: 418's fields plus `measured_tcv_ml`, `reprocessing_agent`, `disinfectant_contact_minutes`, `disinfectant_concentration_pct`, `baseline_tcv_ml?` (mid-life enrolment only), `acknowledgement?: { reason }`, `expected_version?`. Behaviour, in order:

- **Dark** (no policy for `dialyser` **and** no register row for the category, §4.2) → the legacy path, byte for byte (free-text serial, typed count, upsert; `release_status = 'legacy'`). **Deactivated** (a policy that was on; devices exist) → the platform path below, which settles the usage and cannot release.
- **End of use is a precondition.** The session must be `completed` with `actual_end_at`. An aborted in-progress session uses existing `completeSession` with `early_termination = true` and a required reason; its same transaction closes the usage and returns the device to `awaiting_reprocessing` or `quarantined`. Reprocessing is recorded only afterward. `cancelSession` remains pre-start only. `recordReuseRegister` on `main` currently checks no session status, so this is an explicit behavior change.
- **Policy on, session has an open usage** → the device is the usage's device; `reuse_cycle_count` in the body must equal `usage.reuse_cycle` or be absent → else 409 `DIALYZER_REUSE_CYCLE_DERIVED` (behaviour change; the admin modal renders the count read-only).
- **Policy on, no usage** → `recordReuseRegister` refuses `RPD_USAGE_REQUIRED`. Retrospective history uses the separate `POST /api/v1/dialysis/sessions/:id/dialyser/retrospective-use` command: it requires the serial, actual-use interval, recorder and deviation reason; records the occurrence even when it would not have been authorised; sets `capture_provenance = 'retrospective'`; immediately returns it to `awaiting_reprocessing` or `quarantined`/`discarded` according to live holds and protocol; and never makes it available or claims the past use was safe. The census counts it.
- **Three decisions, re-resolved live inside the transaction** (§5.3; the frozen `reuse_screen` is not consulted, so a marker recorded since capture reaches this record): (1) the `Decision` (evidence); (2) nothing — routing is not a post-use question; (3) `reuseEligibilityTx` — may this dialyser be reprocessed for this patient: the protocol matrix over the class (in-process), `surveillance_overdue`, the device's active holds, the ceiling. `computeDispositionOptions` turns the verdict and the domain rule into the allowed set; the `Decision` acted on is frozen as `post_use_screen`. Body `status = 'in_use'` asks for `reprocess`; `discarded` asks for `discard`; `quarantined` asks for `quarantine`. A request outside the allowed set → 409 `RPD_DISPOSITION_NOT_ALLOWED` carrying `allowed`, `discard_reason`, `blocked_code` and the eligibility `verdict` code (never a class or a marker). `reprocess` under `unknown + warn` requires `acknowledgement.reason`; a matrix `no_reuse` cannot be acknowledged.
- **`quarantine` closes the usage first (review 2026-09-06, point 7):** device `return` (`in_case → awaiting_reprocessing`; the usage closes with the quarantine disposition), then `quarantine` (`awaiting_reprocessing → quarantined`, `quarantine_reason = 'exposure_hold'`), one transaction, plus a hold row (§5.5: `hold_type = 'bloodborne_exposure'`, `reason_code = 'exposure_at_return'`, `source_usage_id`) and `exposure_flag = true`. Nothing names the marker. The 418 row is written with `status = 'quarantined'`, `release_status = 'quarantined'`.
- **`discard`**: device `return` then `discard` (reason from the verdict — `bloodborne_exposure`, `max_cycles_reached`, or `other`), usage disposition accordingly; `exposure_flag` set when the reason is exposure; no marker anywhere.
- **`reprocess` — the release criteria (review 2026-09-06, point 6; §4.2a).** The device goes `return` (→ `awaiting_reprocessing`) and is released to `available` by `releaseToAvailableTx` (§5.6) only when every mandatory item is present and passing: eligibility; integrity; baseline TCV established before first use or from the immutable `manufacturer_nominal` / `validated_model_baseline` scope (never the first mid-life measurement); measured TCV at the protocol threshold (default and floor 80%); approved agent, concentration and contact time; current device scope/IFU; residual-test obligation; and the action-specific ceiling. Missing/out-of-bounds evidence is `not_established` and leaves the device non-available; low TCV or failed integrity discards. The occurrence is recorded even when readiness release is refused (§5.6).
- **Attempts — `POST /api/v1/dialysis/dialysers/:deviceId/reprocessing-attempts`** (scope `dialysis_reprocessing_attempt`; roles `DIALYSIS_ROUTE_ROLES`; the device is the subject — the route writes the same per-patient PHI access rows the history read writes, §6.4). Body: the release-criteria fields plus `expected_version`. Preconditions: the device is `awaiting_reprocessing` or `in_cssd`, its most recent usage is settled, **no active hold** (a *released* hold with `release_requires_processing` is what this attempt satisfies — `authorising_hold_id`), the policy is active → else 409 `RPD_ATTEMPT_NOT_ALLOWED`. Writes an append-only `dialyser_reprocessing_attempts` row (`attempt_no` = previous + 1) with the verdict; a `released` verdict runs the same `releaseToAvailableTx`, records the processing event, marks the authorising hold `satisfied`; the original 418 row remains unchanged and readers derive the later release from the append-only attempt/event. This is the recovery path the review asked for: *settled as quarantined → hold released by IC → attempt → released*, with nothing rewritten.
- The 418 row is upserted as today with `device_id`, `device_usage_id`, `reuse_cycle_count = usage.reuse_cycle`, `session_reuse_count = usage.reuse_cycle`, the TCV / agent / protocol / provenance fields; **a second write for a session whose usage is already returned** answers the stored row with 409 `DIALYZER_REUSE_REGISTER_SETTLED` unless the body is identical (`notes` may still be edited). Audit `dialysis.reuse_register.recorded` (metadata: disposition, verdict code, `release_status`, `tcv_pct`, `decision.status` — never reasons, markers or a class); realtime `reuse-register-updated`; the response carries the command receipt (§5.8).

**Read** — `GET /api/v1/dialysis/sessions/:id/dialyser` returns `{ usage (projected, §3.5), device (no marker field exists on it), link: { dedicated_patient_uid, baseline_tcv_ml, baseline_tcv_source }, holds: [{ id, hold_type, reason_code, status, placed_at }] (the marker pointer only for audience roles), reuse_restriction (the live Decision, projected), reuse_eligibility: { verdict } (a code), allowed_dispositions, release: { residual_test_pending, last_release_status }, isolation: { codes, isolation_warnings, warn_only, enforcement_enabled, override } }` or `{ usage: null, … }` when nothing is captured. `isolation` is not projected because it carries no class to project (§3.4, §3.5): this read does **not** pass `includeIsolationClass`, so its `Decision` has no class to publish, and the warnings — `required_group` included — are read back from the session row and re-serialised through the one serialiser. DEPENDS ON Phase 1. The existing `GET /sessions/:id/reuse-register` is unchanged in shape and gains the new columns.

**Cancel** — `POST /api/v1/dialysis/sessions/:id/cancel` (existing route, existing guard). `cancelSession` moves from the bare client into `setTenantTx` with the session locked `FOR UPDATE`; after the status walk is checked and **before** the status `UPDATE`, `dialysisReuseService.onSessionCancelledTx(tx, { session, target, context })` runs:

1. No usage row for the session → nothing (nothing was captured, or the feature is dark). The cancel proceeds as today.
2. The session's usage is already closed (`returned_at` set), **or** a `dialyzer_reuse_register` row references `device_usage_id = usage.id` → 409 `RPD_USAGE_NOT_CANCELLABLE`. Use was recorded on this session: the statutory row says the dialyser was used here, and `cancelled` would contradict it. Such a session ends by `complete`, not `cancel`.
3. An `in_progress` session is never cancelled. The supported termination is `completeSession({ early_termination: true, early_termination_reason })`; before its session update commits, `onSessionEndedTx` closes the usage and returns the device to `awaiting_reprocessing` or `quarantined`. No reprocessing record is a prerequisite, so the flow is not circular.
4. Only a `scheduled` session (`cancelled` / `no_show`) restores an unused capture. `pack_condition` is the standard request field in both domains: `sealed_unopened` preserves prior readiness when no hold or other obligation exists; dialysis `not_connected` proves no patient use but does **not** prove unopened/sterile, so it closes the usage to `awaiting_reprocessing`, clears episode residual evidence, and requires a fresh cycle. Missing evidence is `RPD_PACK_CONDITION_REQUIRED`; invalid evidence is `RPD_PACK_CONDITION_INVALID`. `restoreUnusedCaptureTx` is a dedicated branch over the shared transition primitive, not `releaseToAvailableTx`: it creates no processing event, ignores policy deactivation for safe return, preserves the cycle, rechecks holds/obligations, and lands `quarantined` when a hold arrived.

Every refusal runs before cancellation writes. A refused restoration fails cancellation; a successful restoration closes the usage and clears `current_usage_id`. Only `sealed_unopened` plus still-valid readiness and zero obligations may restore `available`; `not_connected` never does.

**Machines** — `GET /api/v1/dialysis/machines`, `POST /machines`, `PATCH /machines/:id` (scope `dialysis_machine`), roles `DIALYSIS_MACHINE_ADMIN_ROUTE_ROLES` = `DIALYSIS_ROUTE_ROLES ∩ {NURSING_INCHARGE, IP_INCHARGE, ICU_INCHARGE, ADMIN, SUPER_ADMIN}` (an intersection, so the gate can never be dead). `POST /machines` and `PATCH /machines/:id` accept `isolation_group` — a label from the tenant's **approved** vocabulary (`reprocessing_domain_settings.approved_isolation_groups`, §4.1), `null` for a general machine; a label outside it is refused (`RPD_ISOLATION_GROUP_NOT_APPROVED`), and no isolation class is accepted anywhere. Retiring a machine while `block` is on and it is the last active carrier of a mapped group is refused (`RPD_ISOLATION_BLOCK_PRECONDITIONS`, §3.4). `PATCH /sessions/:id/machine` `{ machine_no, isolation_override_reason? }` re-evaluates §3.4 and is on the session guard.

### 5.2 OT (existing CSSD writers plus one authoritative load-outcome handler)

**Enrolment and reservation.** Every hook first looks up an existing platform device/usage before consulting the current policy; policy deactivation cannot fall back to legacy behavior. On first enrolment of an existing set with `last_passed_load_id`, the hook imports a `legacy_readiness_import` event linked to that exact load with `counts_cycle = false`; it becomes `last_processing_event_id` and the first platform usage's `ready_processing_event_id`. A set without known passed-load evidence remains non-available until processed. `issueSet` is reservation only and records the schedule/patient/set/device consistency under composite deferrable keys.

**Actual-use boundary.** `markTheatreUse` is the fourth lifecycle hook. Before the issue becomes `in_theatre`, it acquires the patient advisory lock, synchronously reconciles committed exposure applications or refuses, then locks load→issue→set→device and revalidates current readiness, active holds, patient association, protocol/device scope and `deviceEligibilityTx({ action: 'use' })`. A hold or readiness invalidation after issue therefore prevents physical use. A prion/CJD concern detected at assessment or return synchronously places the marker-neutral operational `specialist_contamination_hold`; it does not wait for a late bloodborne event.

**Return and cancellation.** Return re-resolves current evidence and records one of the domain table's dispositions. Function failure is a separate hold from sterility. Cancellation is allowed only before `markTheatreUse`: `pack_condition = 'sealed_unopened'` may call `restoreUnusedCaptureTx`; any other valid condition, including `not_connected` where the domain supports it, requires ordinary return/processing. Missing/invalid input uses `RPD_PACK_CONDITION_REQUIRED` / `RPD_PACK_CONDITION_INVALID`; there is no `pack_opened` boolean or `RPD_UNOPENED_CONFIRMATION_REQUIRED` alias.

**One outcome handler.** Both `createSterilizationLoad` (which can create passed/failed) and `transitionSterilizationLoad` call `applyLoadOutcomeTx` inside their transaction. Discovery plus a pinned population snapshots every existing load-outcome writer, while deep tests prove semantics. For enrolled sets, existing direct updates to `instrument_sets` and `set_issue_log` are conditional on the handler's per-device result; they cannot independently mark an enrolled set ready after `held`, `not_applicable` or `invalidated`. Unenrolled/dark sets retain the existing CSSD updates.

Handler order is decisive:

1. If the effective load outcome is now failed and an occurrence exists, append one `device_processing_event_revisions` invalidation for the new load revision. Do not increment a cycle. Follow every usage whose `ready_processing_event_id` names the original occurrence, regardless of the device's current state or most recent return. Place/associate load-invalidated holds, block further admission, enqueue patient alerts and infection-control notification, and preserve idempotency on replay.
2. If the outcome is an unchanged pass and the occurrence exists, return `already_counted`; no event, revision, cycle or release repeats.
3. For a new passing occurrence, temporal applicability (`completed_at >= last_returned_at`) applies. Record the physical occurrence even if policy deactivation, a hold or another obligation prevents release. Readiness authorisation occurs only through §5.6. A forbidden cycle creates its hold; cycle ceilings are applied only to the `reprocess` action.
4. A fresh failure with no earlier occurrence places `sterilization_failed` holds on the sets/devices in scope and starts the same minimum response. Running/planned/cancelled outcomes create no processing occurrence.

The CSSD mutation response remains patient-blind: `affected_devices[]`, aggregate `affected_usage_count` / `affected_patient_count`, and `investigation_id` only. Patient/case rows are served by access-logged `GET /api/v1/reprocessing/load-investigations/:id/affected-usages` under the evidence-review role set. The audit record reachable from CSSD also contains only device IDs and aggregate counts. Before activation, every protocol that requires a wider suspect interval defines and tests a report/manual workflow from the failed load back to the last acceptable biological indicator; the investigation route produces that interval and IC records its closure. A richer dashboard remains deferred.

### 5.3 Three decisions and explicit domain dispositions

**Evidence** is the Phase 1 v2 decision for dialysis or `resolveReuseStatus` for OT. **Routing** is `computeIsolationWarnings` after `cohortCompatibilityTx`, using the protected infection profile to produce only an opaque group. **Use/reprocess eligibility** is `deviceEligibilityTx({ action })`; `action = 'use'` ignores the next-cycle ceiling but checks readiness/holds/scope, while `action = 'reprocess'` checks ceiling, protocol matrix, surveillance currency and obligations. Neither result exposes a marker.

| Domain | Evidence/rule | Return disposition | Availability consequence |
|---|---|---|---|
| dialysis | `restricted`, matrix `no_reuse` | discard, or quarantine only when the approved policy explicitly permits adjudication | never reprocess through acknowledgement |
| dialysis | `unknown` + `warn` | reprocess only with recorded acknowledgement, or discard | release still requires all clinical evidence |
| dialysis | `unknown` + `block_return` | return then `serology_required` hold; discard remains an explicit alternative | never discard-only by implication; never available until adjudicated and processed |
| OT | `restricted` | policy's quarantine/discard rule; a post-issue change creates `post_issue_restriction` | ordinary bloodborne status does not impose dialysis's permanent no-reuse matrix |
| OT | `unknown` + `warn` | normal return/reprocessing | universal precautions plus protocol criteria |
| OT | `unknown` + `block_return` | return then `serology_required` hold; discard is explicit | never the bloodborne-exposure disposition |
| either | active hold | quarantine/discard as authorised | no use or readiness release |

Evaluation checks active holds first, then action-specific ceiling with an explicit non-null guard, then evidence/protocol. Cath parity is asserted only over the truly shared input domain; outside it, Plan 4 expectations are explicit. HBsAg, HIV and mixed dialysis cells are locked to `no_reuse`; HCV is conservative `no_reuse` unless an approved immutable protocol permits dedicated reuse. OT protocol shape has no dialysis matrix and uses standard validated processing; prion is a separate specialist pathway.

### 5.4 Overrides

Every `acknowledgement.reason` and `exposure_acknowledgement.reason` is written to `medication_safety_reviews` with `review_type = 'reprocessable_device_reuse'`, `finding_code` ∈ `BLOODBORNE_RESTRICTED_OVERRIDE` (HCV `dedicated_reuse` acknowledged), `SEROLOGY_UNKNOWN_ACKNOWLEDGED`, `EXPOSED_DEVICE_REUSED` (an OT set issued to a restricted patient under `override_allowed`), `ISOLATION_EMERGENCY_OVERRIDE` (§3.4), `override_required = true`, `payload.domain`, and the actor — the cath spec §7.5 shape with a domain field. `review_type` is `VARCHAR(80)` with no CHECK (269:196), so no migration is needed for the new value.

### 5.5 Historical exposure, active holds and processing obligations

`exposure_flag` is immutable history and never authorises or refuses an operation. Active `reprocessable_device_holds` are current restrictions; released holds may leave processing obligations. Every hold release records an authorised adjudication, immutable protocol revision where processing is required, evidence references, actor and time. Operational readers receive only `projectHoldForOperationalRole`; exact evidence is confined to the access-logged evidence-review route (§3.5).

`releaseHoldTx` releases only the named hold. It never writes `available`. If the device is quarantined it moves to `awaiting_reprocessing`; then `evaluateOutstandingObligationsTx` reports all remaining reasons: active holds, released-but-unsatisfied processing obligations, dirty/not-connected return, invalidated readiness, missing/failed residual evidence, protocol revision/device-scope mismatch, or a protocol-specific pathway still incomplete. `release_requires_processing = false` removes only that erroneous hold's obligation. Each satisfied obligation gets an append-only `reprocessable_hold_satisfactions` row pinned to the same device, exact required protocol revision, authorisation time, and a later processing event; a passed load predating the release cannot satisfy it. Prion requires its specifically authorised pathway event, never an ordinary passed load.

Acceptance is full lifecycle: exposure → active hold/refusal → authorised release → still non-available while obligations remain → applicable protocol processing → satisfaction → availability → successful re-issue, while `exposure_flag` remains true. `erroneousHoldReleaseKeepsProcessingObligation.deep.test.js` proves an erroneous release cannot erase an independent dirty-return, fresh-cycle, residual, invalidated-readiness, or protocol obligation.

### 5.6 Occurrence recording, readiness authorisation and unused-capture restoration

There are two deliberately separate branches over the transition primitive:

- `releaseToAvailableTx` is processing-based release only. It records the physical `device_processing_events` occurrence even when a deactivated policy, active hold, invalid device scope, or outstanding obligation prevents readiness authorisation. It then evaluates domain evidence and all obligations. For dialysis it delegates through the statutory row or append-only attempt and applies the approved release criteria. For OT it requires the applicable set/load occurrence, exact active protocol revision/device scope, completed-after-return timing, allowed cycle, and function/sterility evidence. Only a passing occurrence with every obligation satisfied may apply `reprocessed → available`; otherwise the occurrence remains historical and the device remains non-available. The generic `POST /reprocessable-devices/:id/reprocessed` resolves the domain and delegates to those commands; it contains no alternate release logic.
- `restoreUnusedCaptureTx` handles only a scheduled/no-show usage that never began. It creates no processing event, does not apply reprocessing eligibility or cycle ceiling, and remains callable during policy deactivation so tracking can settle. `pack_condition = 'sealed_unopened'` may restore the prior still-valid readiness only when `evaluateOutstandingObligationsTx` is empty. `pack_condition = 'not_connected'` proves no patient connection but not sterility: it clears episode residual attestation and lands `awaiting_reprocessing`. Any hold arriving while captured lands the device `quarantined`. The standard errors are `RPD_PACK_CONDITION_REQUIRED` and `RPD_PACK_CONDITION_INVALID`; `pack_opened` is not a request field.

The release call-site pin therefore asserts: no path sets `available` outside the shared transition primitive; every processing-based release calls `releaseToAvailableTx`; every unused restoration calls `restoreUnusedCaptureTx`; neither function calls the other; and the generic command delegates by domain. Policy hooks first discover whether an existing platform enrolment/usage exists and settle it even when the current policy is inactive; only a truly dark, never-enrolled category may take the legacy early return.

### 5.7 Durable exposure delivery and the admission safety boundary

The marker writers acquire the tenant/patient advisory transaction lock, write marker plus outbox atomically, and then may invoke the fast path. Each consumer registers a stable ID and returns an explicit result containing remaining device work and durable alert/notification obligations. `bloodborne_exposure_deliveries` records that result per event/handler; an outbox row is complete only when every currently required stable handler has zero remaining obligations. Dispatcher promise resolution is never treated as success. The cath consumer is updated only for compatibility: it returns failures instead of swallowing them and treats `tested_on = NULL` as an unbounded legacy lookback.

Replay identity is `bloodborne_exposure_applications (event, handler, device)`, not active-hold uniqueness. Applying a new event may create or associate a new restriction and preserves every evidence-source association; replaying an already applied event cannot create another hold even if the earlier hold was released and processed. The async reconciler uses leases/backoff/redrive and runs from the scheduler, the #1017 operator sweep, and the governance drain route, but it is recovery and notification delivery—not the admission guard.

Every actual-use admission (`startSession`, `markTheatreUse`, and retrospective recording's current-state settlement) acquires the same tenant/patient advisory lock before device rows. It synchronously reconciles relevant committed applications or refuses `RPD_EXPOSURE_RECONCILIATION_PENDING`, then revalidates holds, device readiness, dedication, protocol/device scope, residual evidence and action-specific eligibility. Thus a marker commit and admission are serialised; a queue read racing an uncommitted marker is not relied upon. `exposureAdmissionBoundaryCrash.deep.test.js` commits A's marker, crashes before drain, and attempts B's actual issue/start before drain; use is refused or the restriction is synchronously applied, and later drains are exactly-once.

### 5.8 Complete lock order, conflict-safe enrolment, receipts and races

The order covers the full transaction call graph, including existing CSSD UPDATE/FK locks and nested hooks: (0) tenant/patient advisory lock when patient exposure is relevant; (1) dialysis session, or for OT the relevant sterilization load(s) ascending; (2) OT issue row(s) ascending; (3) instrument set row(s) ascending; (4) platform device row(s) ascending; (5) usage rows; (6) holds and hold satisfactions; (7) dialysis links; (8) statutory/attempt/operation appends. `transitionIssue` pre-reads identifiers without locks, locks its readiness load before issue then set, and revalidates; `transitionSterilizationLoad` locks load, issue rows, then sets. No path locks issue→set while another locks set→issue. The discovery pin inventories SQL writers and UPDATE targets, but semantic confidence comes from the transaction tests, not regex alone.

Unseen-serial enrolment uses `INSERT ... ON CONFLICT DO NOTHING RETURNING`, then selects/locks by serial and revalidates dedication/readiness; it never catches a uniqueness error and continues inside an aborted transaction. Every change to safety evidence, hold/source association, readiness, protocol binding, or status increments `reprocessable_devices.version`. Accepted commands also insert `reprocessable_device_operations` in the same transaction and return its `operation_id`; `GET /reprocessing/operations/:operationId` is the durable proof and replay lookup. Version mismatch remains `RPD_VERSION_CONFLICT`, but a changed version alone is explicitly not proof that a particular command succeeded.

Concurrency tests run two connections with barriers, twenty iterations each: (1) concurrent unseen-serial capture yields one device/open usage; (2) exposure versus hold release/processing never ends available with an active or unsatisfied obligation; (3) issue versus load outcome yields a temporally valid readiness event or a non-applicable result; (4) return versus load outcome follows the same load→issue→set order and never authorises pre-return processing; (5) overlapping multi-device loads lock sorted IDs and neither deadlock nor double-count. These supplement the five named Revision 2 closure tests in §1.3.

**The response validator is named (review 2026-09-06, additional conditions).** `additionalProperties: false` in an overlay is a validation rule, and nothing at runtime validates a response against it. The validator this lane relies on is **`apps/backend/src/tests/helpers/assertSchema.js`** — `assertResponse(method, path, body, status)` and `assertData(schemaName, data)`, an ajv (`strict: false`, `allErrors`) compiled over the generated `src/docs/openapi.json` — extended by this lane with `assertErrorBody(code, body)` for the error envelope (`RpdError`: `{ success: false, code, message, details }`, with `details` declared per code and `additionalProperties: false`). It is exercised in three places: (a) `reprocessableDevicesOpenApiContract.test.js` validates a success fixture for **every** operation in the overlay **and** every documented error body, including the nested `isolation_warnings[]` items, the projected `reuse_screen` / `post_use_screen`, `holds[]`, `receipt` and `affected_devices[]`; (b) the canary harness passes every 2xx and 4xx body it walks through `assertResponse` (a test-only `openapiResponseGuard` in `tests/helpers`), so an unprojected or over-wide body fails the schema before the sentinel is even consulted; (c) both deep suites call `assertData` on the objects they read back. There is deliberately no production response-validation middleware: the cost is a schema compile per route and the failure mode (a 500 on a live clinical read) is worse than the defect it would catch; the tests are the enforcement, and they are named here so nobody mistakes the overlay for one.

### 7.3 Rollout defaults

- Dark by default: no `reprocessing_domain_policies` rows → nothing is minted, the CSSD hooks do nothing, the dialysis reuse-register route runs its legacy path. A tenant activates a domain by creating policy rows **under an approved protocol** (§4.2a) — stage 3 of §1.2; the quality or infection-control officer owns that step. **Deactivation** (a policy switched off after devices exist) stops enrolment and release and keeps tracking and settlement (§4.2).
- Settings defaults when no row: dialysis `discard` / `warn` / 90 / `warn`; OT `quarantine` / `warn` / 90 (the dialysis 90 has no consumer while Phase 1's rule is window-less, §4.1); `isolation_groups` defaults to `{}` on both, so an unmapped unit routes by "any isolation machine" (§3.4).
- Isolation is `warn` until a tenant flips it; unregistered machines warn only for restricted patients; `unknown` patients raise nothing per session (§3.4).
- **Phase 1 dependency.** Every dialysis isolation and post-use decision reads the Phase 1 resolver; this lane's dialysis arm is gated on Phase 1 being on `main` (§3.3), and with a dialysis policy on but no resolver importable the capture, reprocessing, schedule and start paths fail closed with `RPD_ISOLATION_RESOLVER_UNAVAILABLE` (§7.1) rather than fall back to the columns. The OT arm has no such dependency. Nothing here writes the roster; there is no sync and no backfill in this lane. The census script (§7.6) is the Phase 2 gate for the future DROP, not a prerequisite for this lane.
- **Q1 as revised (owner, 2026-09-06; Phase 1's rule, §3.3):** a legacy `'positive'` restricts on its own; a legacy `'negative'` is **not evidence**, so a roster row with only the enrolment default and no marker or `dialysis_serology` row resolves `unknown`. Day-one amber is therefore **higher** than the literal Q1 predicted, and under `unknown_serology_rule = 'warn'` each such patient's first dialyser reprocessing needs an acknowledgement; this document states the fact and makes **no blanket acknowledgement-cost claim either way**. `serology_validity_days` remains inert for dialysis under the window-less Phase 1 rule (§4.1).
- **Release CI fails when activation is possible and the resolver is missing (review 2026-09-06, additional conditions).** `scripts/ci/check-dialysis-activation-gate.mjs` runs in `ci.yml`'s check chain: if `apps/backend/src/services/clinical/dialysisReuseService.js` exists (the dialysis arm is on the build, so a tenant *could* create a dialyser policy) and `dialysisIsolationResolver.js` does not, the job **fails** — it never passes with the dialysis suite skipped. In CI the dialysis deep suite runs under `RPD_REQUIRE_PHASE1=1`, under which a missing resolver is a failing test, not a `describe.skip`. And at boot, `dialysisActivationGuard.js` (the `exposureHandlerBootstrap` pattern from #1017) refuses to start an API whose database holds any `reprocessing_domain_policies` row with `domain = 'dialysis' AND reprocessable = true` while the resolver is unimportable — a deployed build cannot be one migration away from a fail-open.
- **The activation write itself is the final capability gate.** The transaction that first sets a policy `reprocessable = true` verifies the accepted resolver contract version, physical-use admission hooks, required stable exposure consumers and zero incomplete capability registrations, active immutable protocol/device scopes, prion/suspect-interval workflow where applicable, and validated isolation mappings when block mode is requested. It refuses atomically with `RPD_ACTIVATION_CAPABILITY_MISSING`; file existence, CI and boot checks are additional defences, not substitutes.
- No data migration of 418 rows: legacy rows keep `device_id NULL`.
- Existing instrument sets get register rows on their next issue after a policy exists, at `cycle_count = 0` with `enrolled_from_existing_set` — the count starts from enrolment, which is stated on the row.

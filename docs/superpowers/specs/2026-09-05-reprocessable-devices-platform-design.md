## 1. Problem and scope

The platform holds **four independent reprocessing loops with four incompatible identity models**, built at four different times:

| | cath (Plan 2, mig 765) | dialysis (mig 418) | OT/CSSD (migs 421–423) | linen (migs 473–474) |
|---|---|---|---|---|
| identity | system-minted `device_tag` `RP…` | operator-typed `dialyzer_serial` free text | `set_code` + `barcode`, operator-supplied | none (quantity) |
| grain | one row per physical device | one row **per session** | one row per set + one issue row per OT case | per laundry cycle |
| state machine | 6 states, `DEVICE_ACTIONS` from-lists | 3 flat statuses | 9 on the set, 7 on the issue | 5 on the cycle |
| cycle ceiling | `max_cycles_snapshot`, DB CHECK | `reuse_cycle_count` 0..100, typed, no policy | none | none |
| serology gate | full (`resolveReuseStatus`) | none — parallel `dialysis_patients.*_status` columns, never consulted by the reuse path | none | none |
| sterilisation evidence | manual CSSD mark, no load link | `integrity_test_result` pass/fail, `disinfectant` free text | `sterilization_loads` with BI/CI/mechanical indicators | none |
| per-patient dedication | pooled | recorded (`patient_uid`) but never enforced | pooled | pooled |

Plan 4 is **convergence, not extension**: one register, one policy shape, one state machine, one serology gate and one CSSD queue serving dialysis and OT, with the cath register left where it is. Linen stays quantity-based and is out of scope.

The three defects this closes, in order of clinical weight:

1. **Dialysis has no serology gate and two serology records that disagree.** `dialysis_patients.hbsag_status / hcv_status / hiv_status` (168:45-50) drive `isolation_required` and the today board, but a reactive HBsAg signed off in the lab updates `patient_bloodborne_markers` (Plan 1) and *not* those columns. A patient the platform knows is reactive can sit on the board as non-isolation. The dialyser reuse path (`dialysisService.recordReuseRegister`, :928-999) reads neither record. This defect has two halves and two owners: *which record the roster reads* (the derivation) is the Phase 1 lane's, and *the reuse path reading no record at all* is this lane's — closed by consuming Phase 1's resolver (§3.3).
2. **The dialyser cycle count is whatever the operator typed.** `reuse_cycle_count` is validated only against `dialysis_sessions.reuse_count`, a number the same client wrote on the previous call (:945-957). Nothing links two register rows carrying the same serial; nothing stops one serial appearing under two patients; there is no maximum, no TCV rule and no agent/contact-time record.
3. **OT sets carry no cycle count, no exposure flag and no policy**, and a set used on a reactive patient is returned and re-issued like any other. Sterilisation evidence exists (`sterilization_loads`, 422) but cath devices are not on it, and a failed load does not touch a set already issued.

The unmerged `audit/cath-implant-lifecycle` branch (which carries a colliding migration 764) is decided separately by the owner (D5b); nothing here depends on it or touches its tables.

## 2. Decisions

The owner's decisions are fixed; the reasons recorded here are the scouting brief's, kept so the migration header can state them inline.

- **D1 — Owner references are typed, nullable per-domain FKs plus `CHECK (num_nonnulls(...) = 1)`.** The pattern is already in production on `surgical_implants` (`565:54-58`, `surgical_implants_source_check`). A `(ref_type, ref_id)` string pair cannot be a foreign key; three sibling registers cannot share a queue. Every arm is a tenant-pinned composite FK (§2.4).
- **D1b — Cath stays in `cath_reprocessable_devices`.** Two registers, one service shape, one queue with a domain filter. The seam for a later cath migration is §2.6.
- **D2 — The register is patient-blind.** Per-patient dedication of a dialyser lives on the dialysis link row (§2.5), never on `reprocessable_devices`. This is what keeps `/api/v1/cssd` free of a PHI logger and keeps the CSSD queue out of the serology disclosure blast radius.
- **D2b — Domain is a fixed enum**, `dialysis` and `ot`, with `cath` reserved. Per-domain rules are code, not configuration; a tenant seeding a "Nephrology 2" department must not create a fourth rule set.
- **D3 — Dialysis machines do not enter the register.** A minimal `dialysis_machines` table (§2.7) carries the isolation class; isolation is **warn-only with a recorded override**, mirroring `set_issue_log.warn_only / enforcement_enabled` (423:27-28), with a per-tenant switch to `block` for units that have tagged their machines.
- **D5 — OT scope is instrument sets plus the sterilisation-load evidence FK on `surgical_implants`.** Implant reuse is out of scope.
- **D6 — Dialysis converges: mint device identities for dialysers; `dialyzer_reuse_register` stays as the statutory log and gains `device_id`.** `reuse_cycle_count` becomes derived from the device, which is the defect being closed. Two behaviour changes follow and are flagged in §4.2: a client-typed cycle count that disagrees with the device is refused, and a register row stops being freely re-writable once the device has moved on.
- **D7 — Sterilisation evidence is load-driven for OT and not for dialysis.** OT sets are already on `sterilization_loads` (`set_ids`, `instrument_sets.last_passed_load_id`, `set_issue_log.sterilization_load_id`); a passed load increments the set's device cycle and a failed load quarantines it. Dialyser reprocessing is a chemical reuse-room process recorded on the statutory row, not an autoclave load.
- **D8 — Billing unchanged.**
- **D9 — External identifiers are accepted alongside the minted tag.** `manufacturer_serial` (dialysers) and `hospital_asset_id` (the OT set barcode is copied here) are unique per tenant and domain when present; the minted `device_tag` is always present.
- **D10 — PENDING, owner.** Admit `DIALYSIS_TECHNICIAN` (and, by the same argument, `BLOOD_BANK_TECHNICIAN` / `BLOOD_BANK_STAFF`) to the serology audience via the reviewed 35-entry allow-list in `serologyDisclosureCanary.test.js` — a one-line, reviewed widening, tied to the role-assignability decision in §9.1. The shipped design is correct under either answer: the projection in §3.5 blanks marker *values* and lab evidence for non-audience roles and nothing else, so widening the audience changes who reads a value, not what any route computes or which machine a patient is routed to.
- **D11 — PENDING, owner. May a routing role learn *which* marker isolates a patient, or only *that* one does?** Whoever puts a patient on a machine must know the patient needs an isolation machine; whether the *reason* may be named to that role is a separate question, and it is the owner's. **YES** → the user-facing `isolation_warnings.required_class` may carry the marker class (`hbsag` / `hcv` / `hiv` / `isolation_mixed`) — the shape review round 1 settled on (Fix-6); nothing else in this design changes. **NO** → the machine layer becomes marker-agnostic: `dialysis_machines.isolation_group` replaces `isolation_class` as the routing key (a tenant-defined label — "Bay 1", "Red side" — carrying no clinical meaning); the class → group mapping lives in this lane's per-tenant isolation settings (`reprocessing_domain_settings`, §4.1) and is editable only by `INFECTION_CONTROL_OFFICER` / admin, **never by a technician**; `evaluateIsolationForSessionTx` resolves class → group **server-side**; the warning payload and the mismatch codes name the **group** (`required_group`), the `dialysis.session.isolation_evaluated` metadata names the group (§7.2), and the dialysis device's `exposure_markers` stamp (§3.3) reduces to the flag alone. **The resolver contract in §3.3 is unchanged under either branch** — the class crosses the Phase 1 seam server-side either way; only what leaves the API to a routing role differs. **Default until answered:** server-side routing uses the class through the opt-in `includeIsolationClass` flag, and **nothing user-facing carries it** — the session warning ships in the interim shape of §3.4. Review round 1's Fix-6 ("do not blank `required_class`") is **SUPERSEDED** by D11: that round reasoned the class was recoverable anyway (`GET /machines` publishes every machine's class and the two mismatch codes narrow it by elimination), which is an argument for the NO branch's group relabel rather than for shipping the class.

Decisions taken by this spec within those:

- **A captured device is released, not returned, when its case is cancelled before use.** `cancelSession` / `no_show` (dialysis) and `transitionIssue → cancelled` (OT) run an un-capture hook inside the cancel's own transaction: the usage closes with `post_use_disposition = 'cancelled_before_use'`, the device goes `in_case → available` with no cycle change and no reprocessing record, and a cancelled usage does not consume its cycle number (§4.4). Without this a cancelled case left the device `in_case` with an open usage, and the only exits from `in_case` were `return` (a needless reprocessing) or `discard`: the next `issueSet` of the same sterile set failed `RPD_DEVICE_NOT_AVAILABLE`, the next capture of the patient's own dedicated dialyser failed the same way, and "recovering" by recording reprocessing on the cancelled session incremented a cycle that never happened — the D6 defect re-opened from the other side. The un-capture is refused when use was recorded or may have happened (§5.1 Cancel, §5.2), and a refused un-capture fails the cancel: best-effort is not allowed here, because a cancel that succeeds while the device stays `in_case` is exactly the defect.

- **Two policy tables, not one.** The brief sketched a single `reprocessing_domain_policies (tenant × domain × category)` carrying the serology rule. The serology rule is needed *before a category is known*: the late-reactive exposure handler sweeps a whole domain, and the dialysis isolation warning is evaluated per session, not per device. So the three serology fields live on `reprocessing_domain_settings (tenant × domain)` — the exact shape of `cath_reprocessing_settings` with a domain column — and `reprocessing_domain_policies (tenant × domain × category)` carries reprocessable / max cycles / cycle types / function check / TCV threshold, the exact shape of `cath_reprocessing_category_policies` plus two columns. Plan 2's admin and service code shapes carry over unchanged.
- **A third `reactive_patient_rule` value, `quarantine`.** Plan 2's `discard` means "the device is retired at post-use". Retiring a ₹2-lakh orthopaedic tray because it touched a reactive patient is not what any theatre does; the realistic action is to hold it for infection control, who either release it into a fresh cycle or discard it. Rather than make `discard` mean two things, the enum gains `quarantine`. Dialysis defaults to `discard` (a dialyser is a consumable), OT defaults to `quarantine`; either domain may choose either. The shared disposition function gains one branch; a parity test pins that, with no `quarantine` rule in play, it answers exactly what cath's `computePostUseOptions` answers for the same inputs.
- **`max_cycles` is optional.** Instrument sets have no meaningful cycle ceiling (wear is per instrument, which is not modelled); dialysers do. `max_cycles_snapshot` on the register is nullable and the bound CHECK reads `max_cycles_snapshot IS NULL OR cycle_count <= max_cycles_snapshot`. This is the one place the register's CHECKs differ from 765's; it is stated in the migration header.
- **OT sets get one register row each, linked 1:1 by `instrument_set_id`; `instrument_sets.status` keeps its nine values and the CSSD board keeps reading it.** The register row carries only what the set lacks (cycle count, ceiling, exposure, the six-state reuse status, the last passed load). The two states are kept coherent by four hooks inside `cssdService`'s existing transactions (§5.2) — issue, return, cancel, load transition — and a unit test pins that every `set_issue_log` write path in `cssdService.js` calls the hook. Where they can still disagree (a set edited by a path that does not exist yet) the register's row is the reuse truth and the set's row is the board truth; the device read joins both and exposes `set_status` beside `status`.
- **Dialysis isolation and the dialysis reuse decision consume one resolver, owned by the Phase 1 lane.** This lane writes nothing to `dialysis_patients.*_status`, keeps no sync, no latch and no union read of its own, and reads `resolveDialysisIsolation` (§3.3) for every isolation and post-use decision — live, never from the frozen snapshot. The derivation itself, its migration (767) and its backfill are dev-ea's; the Phase 2 census that gates the eventual DROP is this lane's.
- **The dialysis reprocessing record is one command.** `POST /sessions/:id/reuse-register` (existing) performs post-use and reprocessing together — the reuse room writes one form, and that is the form the statutory row is. Its body gains TCV, agent and contact time; the cycle count becomes read-only.

### 2.6 The cath seam (not built here)

A later migration converging cath would: widen `reprocessable_devices_domain_check` and `reprocessable_device_usages_domain_check` to admit `cath` (drop and re-add by name — the forward pattern 765 used on 564's constraint); add `cath_catalog_item_id` as a third identity arm on the register and `cath_case_id` / `cath_usage_id` as a third owner pair on the usage table with the CHECKs widened to `num_nonnulls(...) = 1` over three; add `legacy_tag VARCHAR(24)` unique per tenant so a migrated device keeps the `RP…` label already affixed to it (the generated `device_tag` cannot be overridden); copy rows; re-declare `cath_inventory_authority_assert_contract_753`'s `reused_device` branch to read the new table; and leave `cath_reprocessable_devices` as a view. Nothing in `NNN` forecloses any of that, and nothing in `NNN` depends on it.

## 3. Serology gate

### 3.1 One resolver

`bloodborneMarkerService.resolveReuseStatus({ tenantId, patientUid, validityDays, asOf, db })` is already domain-free (it is patient-scoped and reads only `patient_bloodborne_markers`). **OT** calls it with the OT `serology_validity_days` from `reprocessing_domain_settings` (`instrument_sets` and `ot_schedules` carry no legacy serology). **Dialysis does not call it at all**: capture, the reprocessing record, the session read and the isolation rule read the Phase 1 resolver's `Decision` (§3.3), whose rule differs from this one on purpose — no validity window, and the retained roster columns as a legacy-declaration input. So "one resolver" is one *per record shape*: the cath resolver for cath and OT, the roster resolver for dialysis; neither lane re-implements the other's. The evidence-freezing rule from the cath spec §7.4 holds, with one sharpening stated in §3.3: `reuse_screen` (capture) and `post_use_screen` (return) on `reprocessable_device_usages` are evidence snapshots, written once and never an input to a later decision; every decision re-resolves live, and a later result changes the device through the exposure handler, never the historical rows.

### 3.2 One exposure handler, two domain arms

`reprocessableDeviceService.quarantineDevicesExposedToPatient(event)` registers with `registerExposureHandler` at module load, exactly as `cathDeviceReuseService.js:1262` does. The registry is already domain-neutral; a second handler is a second `Set` member. For a reactive event `{ tenantId, patientUid, marker, testedOn, markerRowId }`:

- **dialysis arm** — every device whose `reprocessable_device_dialysis_links.dedicated_patient_uid` is the patient and whose status is not `discarded` (no window: a dedicated dialyser is that patient's for life, and the exposure is the patient's own history), plus any dialysis device with an open usage on that patient;
- **OT arm** — every OT device with a usage row for that patient with `captured_at >= tested_on − serology_validity_days` (Asia/Kolkata midnight boundary, the same `AT TIME ZONE` pin as 765), all uses for `cjd_suspected`;
- each candidate is settled in its **own** transaction (the Plan 2 resilience contract: one lock timeout must not roll back nine quarantines): `available` / `awaiting_reprocessing` / `in_cssd` → `quarantine` with `exposure_flag`, the marker appended and `quarantine_reason = 'Late reactive <marker> result dated <date>'`; `in_case` or already `quarantined` → flag stamped without a transition; `discarded` re-checked under the lock and skipped;
- **nothing is written to `dialysis_patients`** — the roster derives its state at read time through the Phase 1 resolver (§3.3), so the handler has no sync step;
- then one `cds_alerts` row (`alert_type = 'bloodborne_reuse_exposure'`, `severity = 'high'`, description naming the domain and tags) and one `notification_outbox` row per active `INFECTION_CONTROL_OFFICER` (`type = 'bloodborne_reuse_exposure'`, `sourceEventKey = 'bloodborne-reuse-exposure:rpd:<markerRowId>:<officer uid>'`, deep link `/dashboard/cssd?tab=devices&domain=<domain>`), raised for whatever subset settled even when others failed.

There is still no outbox between the marker commit and the handler call; a crash in that window loses the push and the pull-style resolver stays correct (cath spec §18). The reconciliation sweep recommended there now covers three domains and is listed again in §10.

### 3.3 Isolation derivation — dependency on the derivation lane

**What changed and why.** The first draft of this section derived `dialysis_patients.hbsag_status / hcv_status / hiv_status` from the marker record inside this lane: a service-side sync with a no-downgrade latch, a union read of the two records during transition, a `dialysis_surveillance` marker source, an enrol-body guard and a one-shot backfill script. That collided head-on with the **dialysis isolation derivation lane** (dev-ea), which owns the same three columns, the same enrolment default and the same roster surfaces. A decision trio (advocate / challenger / supervisor, 2026-09-05) ruled **two-phase**, and this document now designs to that verdict. The lane pick itself — fold the derivation into Plan 4, or carve it out — is recorded as an owner question (§9.6) with the carve as the working assumption.

**Phase 1 — the derivation lane (dev-ea; migration 767).** Not built here; stated so this lane's dependency is explicit:

- A **read-time resolver is the only input to any isolation decision**. The three `dialysis_patients.*_status` columns are **retained, read-only**, as legacy-declaration inputs to a union read inside the resolver. There is **no sync write** onto them and **no no-downgrade latch**: a column is a declaration made by a person on a date, and the resolver weighs it as one input beside the marker rows.
- The isolation rule is **distinct from `computeReuseStatus`** (the cath resolver): a non-voided reactive marker → `restricted`; any non-voided non-reactive → `clear` **regardless of age**; nothing → `unknown`. The cath rule's 90-day `clear` window is wrong for a roster: with zero markers cluster-wide today, a window would leave every marker-less roster `unknown` forever.
- `unknown` **never isolates and never blocks**. Enrolment writes `'unknown'`, not `'negative'` (the `'negative'` default was a claim nobody made). Amber renders as a **roster chip only**; no per-session warning fires for it — `DIALYSIS_SEROLOGY_UNKNOWN` **does not exist** (§3.4). Unknown-isolates would isolate every patient on day one.
- Invariant (d): a voided reactive with **no other evidence** falls back to the **column**, not to `clear` — a void un-isolates only when the marker was the sole evidence.

**The resolver contract this lane consumes** (agreed with dev-ea in full, 2026-09-05 — there is no open point left):

```
resolveDialysisIsolation({ tenantId, patientUids, db,
                           includeMarkers = false, includeIsolationClass = false })
  → Map<patientUid, Decision>            // batch-first; callable inside a tx with the tx client
Decision = {
  status:   'restricted' | 'unknown' | 'clear',
  asOf,                                  // when the resolver evaluated
  reasons:  [],                          // human text; empty unless the caller is in the audience
  evidence: 'marker' | 'legacy_declaration' | 'none',
  isolation_class?: 'hbsag' | 'hcv' | 'hiv' | 'isolation_mixed' | null,
                                         // ONLY when includeIsolationClass === true;
                                         // null unless status === 'restricted'
  markers?: [...]                        // ONLY when includeMarkers === true
}
isolated === (status === 'restricted')   // derived, never stored as a second flag
```

- A thin single-uid wrapper exists for the per-session paths; this lane binds to both through one adapter (`dialysisReuseService.isolationDecisionTx`), so a Phase 1 rename is a one-line change here.
- **No boolean pair.** `{ isolated, unknown }` admits an illegal fourth state; `status` is the one field.
- **Marker detail is opt-in and default off**, so a caller that forgets gets the safe shape. **No caller in this lane passes `includeMarkers: true`.** The one surface that may — the roster / patient-detail read behind `roleSeesSerologyDetail` — is Phase 1's roster work; this lane does not attach a resolver call to the existing `GET /patients/:id` (an existing read must not start answering 503 on a build without Phase 1). The adapter carries the flag so that surface has one seam to use; the session evaluator (`assessIsolationTx`), capture, the reprocessing record, the session read and the CSSD paths never forward it.
- **`isolation_class` is opt-in on the same footing as marker detail, and this lane's ask is settled that way.** Plan 4 first asked for it as an unconditional fifth field. dev-ea refused, and was right: a value of `'hiv'` **is** serology whatever the caller calls it, and "it is a routing instruction, not a marker value" is the same reframing that produced the two earlier disclosures this canary exists to catch. So the field is **present only when `includeIsolationClass: true`**, and **`null` unless `status === 'restricted'`** — a caller that forgets gets the safe shape, exactly as with `includeMarkers`. Phase 1 computes it from the rule this lane hands over: one reactive core marker → its class; two or more → `isolation_mixed`; `restricted` for a marker with no machine class (`cjd_suspected`, other) → `isolation_mixed`; not restricted → `null`.
- **Who may pass `includeIsolationClass: true`.** Only the **session-evaluation path** — `assessIsolationTx`, which does the read, and `evaluateIsolationForSessionTx`, which wraps it for start and reassign (§3.4) — plus the post-use disposition (`recordDialyserReprocessing`), which needs the class for one server-side write, the device's `exposure_markers` stamp (below). Both are server-side decisions: the value picks a machine or stamps a device row and **is never rendered as the patient's required class**. The roster, the today board, the case / session lists, patient detail, capture, the session read and every CSSD path **never pass it**, so their `Decision` has no `isolation_class` key at all. What a routing role may *see* is D11 (§2), not this bullet; until D11 is answered nothing user-facing carries the class (§3.4).
- **The adapter's fail-closed check keys on the ask, not on presence.** `RPD_ISOLATION_DECISION_INVALID` (500) fires when a caller **asked** for the class and the resolver answered without one or with a value outside the four — a real invariant, because a wrong shape must not route a patient. With the flag **off**, a `Decision` carrying no `isolation_class` is **valid**; asserting presence unconditionally would only re-create the rejected contract inside our own code.

**Snapshot versus decision** (dev-ea's fourth point). `reuse_screen`, frozen on the usage row at dialyser capture, is an **evidence snapshot**: "what was known when this dialyser was captured". It is written once, is never re-read as current state, and is never an input to any decision. Both decisions this lane makes for dialysis **re-resolve live** through the resolver: schedule / start / reassign machine routing (§3.4) and the post-use reprocess / quarantine / discard decision (§5.1). The snapshot exists so an audit can see what the capturing user saw; a marker recorded between capture and start must — and does — reach the machine assignment, and one recorded between capture and the reprocessing record reaches the disposition. `post_use_screen` is the same kind of object: the `Decision` the reprocessing record acted on, frozen after the fact. **Neither snapshot carries marker detail, and neither carries `isolation_class`** — the frozen rows are returned raw inside `usage` by `GET /sessions/:id/dialyser`, so a class left on one would publish to every dialysis role the thing D11 has not decided. The two in-process consumers that need the class (the isolation audit metadata and the `exposure_markers` stamp) take it before the freeze.

**Exposure markers on a dialysis device.** `returnDeviceTx` stamps `exposure_markers` from the post-use screen's reactive markers; a `Decision` has none. For dialysis the markers are derived from `Decision.isolation_class` — which is why `recordDialyserReprocessing` is the second and last path that passes `includeIsolationClass: true`: `hbsag` / `hcv` / `hiv` → that one marker; `isolation_mixed` → the flag alone with `metadata.exposure_isolation_class = 'isolation_mixed'` (the CHECK `exposure_flag OR cardinality(exposure_markers) = 0` admits a flagged device with an empty list). The late-reactive handler (§3.2) is unaffected: it stamps the marker its event names. The CSSD queue reads the flag; the class is enough for universal precautions. This stamp is a property of a **device**, not a patient's required class, and it matches what the OT arm already writes from `resolveReuseStatus`; under D11's NO branch it reduces to the flag alone (§2), which is the one thing in this lane besides the warning payload that names a marker to a routing role.

### 3.4 The dialysis isolation WARN rule

Evaluated in `startSession` and `scheduleSession` (both existing) for the session's machine and patient, and re-evaluated by `PATCH /sessions/:id/machine` (new, §6.1). Every evaluation reads a **live `Decision`** from the Phase 1 resolver (§3.3) — never the frozen `reuse_screen` — so a marker recorded between capture and start reaches the machine assignment. **DEPENDS ON Phase 1.** In `scheduleSession` the evaluation runs **before** the `INSERT`, inside one `setTenantTx` (today's `scheduleSession` inserts with the bare client outside any transaction — `dialysisService.js:466-481` — so a `block` refusal raised after the insert would leave an orphan `scheduled` row): `assessIsolationTx` reads and decides without writing, the `INSERT` itself carries the isolation columns, and a `DIALYSIS_ISOLATION_MACHINE_BLOCKED` at scheduling leaves no row (a deep test asserts the count). `startSession` and the reassign route call `evaluateIsolationForSessionTx`, which is `assessIsolationTx` plus the `UPDATE` onto the existing row. Pure function `computeIsolationWarnings({ decision, machine, enforcement })`:

| Condition | Code | Severity |
|---|---|---|
| decision `restricted` and no `dialysis_machines` row for `machine_no` | `DIALYSIS_MACHINE_UNREGISTERED` | warn |
| decision `restricted`, machine registered, `isolation_class` ∉ {`decision.isolation_class`, `isolation_mixed`} | `DIALYSIS_ISOLATION_MACHINE_MISMATCH` (the class stays server-side — see the interim payload below) | warn, or block when `enforcement = 'block'` |
| decision `unknown` | **nothing** — `unknown` never isolates and never blocks (§3.3); the amber state is a roster chip owned by Phase 1, not a session warning | — |
| decision `clear`, machine registered, `isolation_class <> 'general'` | `DIALYSIS_GENERAL_PATIENT_ON_ISOLATION_MACHINE` | warn |

A clear patient on an unregistered machine produces nothing — otherwise every session on day one warns, and a warning nobody reads is not a warning; an `unknown` patient produces nothing for the same reason multiplied by a marker-less cluster. The required class is `Decision.isolation_class`, computed by Phase 1 by the rule handed over in §3.3 (`hbsag → hbsag`, `hcv → hcv`, `hiv → hiv`; two reactive markers → `isolation_mixed`); this lane does not derive it from markers. When the code list is non-empty, `startSession` requires `isolation_override_reason` (400 `DIALYSIS_ISOLATION_OVERRIDE_REQUIRED`) and records it with actor and time; under `block`, a `MISMATCH` refuses with 409 `DIALYSIS_ISOLATION_MACHINE_BLOCKED` regardless of reason. The codes, the mode pair and the override are persisted on `dialysis_sessions` (§2.8) and audited as `dialysis.session.isolation_overridden`.

**The interim user-facing payload (pending D11, §2).** `computeIsolationWarnings` keeps returning `required_class` — it is the value the mismatch test and the `dialysis.session.isolation_evaluated` metadata are made of, and it never leaves the process. What the API emits carries **no class key at all**:

```
isolation: {
  codes:              ['DIALYSIS_ISOLATION_MACHINE_MISMATCH', …],   // the persisted flat list
  isolation_warnings: [{ code, machine_id, severity }],             // one entry per code; NO class
  warn_only, enforcement_enabled, override
}
```

`machine_id` is the `dialysis_machines.id` the warning is about and is `null` for `DIALYSIS_MACHINE_UNREGISTERED`; `severity` is `'warn'` or `'block'` from the table above. The `DIALYSIS_ISOLATION_MACHINE_BLOCKED` 409 carries `{ codes }` and no class for the same reason. Under **D11 = YES** each entry regains `required_class`; under **D11 = NO** it gains `required_group` instead and `machine_id` is joined to a group rather than a class. `DialysisIsolation`'s OpenAPI schema is `additionalProperties: false` (§6.6), so a payload that starts carrying a class fails schema validation before it reaches a reviewer — the shape is enforced, not merely documented.

### 3.5 Projection for non-audience roles

`DIALYSIS_ROUTE_ROLES` admits three roles outside `roleSeesSerologyDetail` (`CLINICAL_STAFF_ROUTE_ROLES`): `BLOOD_BANK_TECHNICIAN`, `BLOOD_BANK_STAFF` and **`DIALYSIS_TECHNICIAN`**. `CSSD_ROUTE_ROLES` admits six (`STORES_PURCHASE_INCHARGE`, `HR_STAFF`, `QUALITY_OFFICER`, `INFECTION_CONTROL_OFFICER`, `DATA_PROTECTION_OFFICER`, `COMPLIANCE_OFFICER`). `THEATRE_ROUTE_ROLES` admits none. Every read surface added or changed by this lane projects by role through the **same predicate** (`cathDeviceReuseService.roleSeesSerologyDetail`, deliberately not a second list), keys blanked never dropped:

- `reuse_restriction` on every payload: `projectReuseRestrictionForRole` (existing) — for OT the cath shape: `status`, `validity_days`, `evaluated_at` survive; `reasons` and `markers` empty. For dialysis the payload is the resolver's `Decision` (§3.3): `status`, `asOf`, `evidence` survive; `reasons` emptied; `isolation_class` **blanked to `null`** for a non-audience role (keys blanked, never dropped) — belt and braces, because no read surface in this lane passes `includeIsolationClass`, so the key is absent on these payloads to begin with. `markers` is never present on these surfaces (no caller in this lane forwards `includeMarkers`; the projection drops the key anyway, and the canary's poisoned Decision carries one so a forwarding route fails).
- `isolation` / `isolation_warnings[]`: **still not projected — because there is now nothing in them to project.** `codes`, `machine_id` and `severity` reach every dialysis role: whoever puts the patient on a machine must know a warning fired and which machine it is about. The class does **not** reach them (§3.4, interim payload) pending **D11** (§2). Review round 1's Fix-6 — "do not blank `required_class`; it is a routing instruction, and blanking protects nothing because `GET /machines` publishes every machine's class and the two mismatch codes narrow it by elimination in at most three attempts" — is **SUPERSEDED** by D11: the recoverability argument is a reason to relabel the machine layer (D11's NO branch), not a reason to publish the class outright, and the same "it is a routing instruction, not a marker value" reframing is what dev-ea rejected on the resolver contract. The canary now pins the *value*, not the key (§3.6).
- `dialysis_patients` rows on roster, today board and patient detail: `hbsag_status`, `hcv_status`, `hiv_status` → `null`; `isolation_required` survives (the advisory). `dialysis_serology` rows in patient detail: `hbsag`, `hbs_titre`, `anti_hcv`, `hcv_pcr`, `hiv` → `null`, `is_seroconversion` → `false`; `test_date` survives.
- The CSSD queue carries no patient identity and therefore nothing to project; the canary proves it (§3.6).

**Consequence the owner must see (D10 and D11).** The dialysis technician is the person who runs the reuse room and, in most units, the person who puts a patient on a machine. Under this projection the technician sees the restriction status and the isolation codes — enough to know the patient needs an isolation machine and which machine the warning is about — but not the marker values, the reasons, the lab rows, or (pending D11) the required class. **D10** asks whether the technician and the two blood-bank roles join the serology audience at all: a one-line, reviewed widening of the pinned 35-entry allow-list in the canary, tied to the assignability question in §9.1. **D11** asks the narrower question for the roles that stay outside it: may the routing role learn *which* marker isolates the patient, or only *that* one does. They are different questions and are answerable independently — a YES to D10 makes D11 moot for those three roles and leaves it live for every other non-audience reader. The design ships the same under any combination.

### 3.6 The canary gains three mounts

`serologyDisclosureCanary.test.js` enumerates exactly three mounts today (`/api/v1/cath-lab`, `/api/v1/stemi-pathway`, `/api/v1/cath-reprocessing`). It gains `/api/v1/dialysis` (`DIALYSIS_ROUTE_ROLES`), `/api/v1/cssd` (`CSSD_ROUTE_ROLES`) and the new `/api/v1/reprocessing` (§6.4). The stubbed persistence layer poisons the dialysis roster row with `hbsag_status = SENTINEL`, a `dialysis_serology` row with `hbsag = SENTINEL`, and both resolvers' stubs — `resolveReuseStatus` for OT and the Phase 1 `Decision` for dialysis — return sentinel-bearing `reasons`, so every unprojected `reuse_restriction` would leak. The disclosure predicate gains **three** checks beside the existing ones: any object carrying a non-null `hbsag_status` / `hcv_status` / `hiv_status` (or a non-null `hbsag` / `anti_hcv` / `hiv` / `hbs_titre` / `hcv_pcr`, or `is_seroconversion === true`); any `reuse_restriction` (or `restriction`) with a non-empty `reasons` or `markers`; and — the D11 sentinel — any node carrying an `isolation_class` or `required_class` whose **value** is one of `hbsag` / `hcv` / `hiv` / `isolation_mixed`. The third mirrors the existing `critical_items` check exactly: a **value** test against a named set (`SEROLOGY_CODES` plus `isolation_mixed`), not a key-presence test, so the key may be absent or `null` and only a marker-class string fails. It carries the same shape guard `serologyItemLeaks` uses: a node with a `machine_no` is a `dialysis_machines` row, whose class is a property of *equipment* and not of a patient (`GET /machines` publishes it, and it is exactly the label D11's NO branch replaces with `isolation_group`), so machine rows are out of scope. The reachable-set snapshot is regenerated deliberately (`CANARY_WRITE_SNAPSHOT=1`, which rewrites and then fails) and the diff read: every new line is a GROWTH, which is expected for three new mounts and nothing else. **Population (liveness):** because no response legitimately carries a patient's class in the interim shape, the D11 value walk has a population of zero by design and proves only absence; the suite therefore also asserts that the sweep VISITED at least one `isolation_warnings` entry (`code` + `machine_id` + `severity`) and at least one Decision-shaped node (`status` + `evidence` + `asOf`), and that an entitled role's body still carries the poisoned `reuse_restriction.reasons` sentinel; a zero count fails as an INERT FIXTURE instead of passing over nothing (the empty-population class). Its mutation: drop `POISONED_ISOLATION` from the mock and the population test, not the value sentinel, goes red.

## 4. Data model

All new tables: `tenant_id UUID NOT NULL` with the GUC default used by 765, `REFERENCES tenants(id) ON DELETE CASCADE`, `ENABLE` and `FORCE ROW LEVEL SECURITY`, the `tenant_isolation` policy verbatim from 765, a role-guarded GRANT block (SELECT, INSERT, UPDATE; DELETE and TRUNCATE revoked; sequence USAGE and SELECT only), registration in `src/lib/prisma.js`'s `runtime_mutable_no_delete_relations` and `runtime_nextval_sequences`, `prismaCoverage.test.js` pins, and `TABLE_COLUMN_SEED_OVERRIDES` entries. Every CHECK is named. Every FK into an existing table is a tenant-pinned composite; composite `SET NULL` actions carry the column list. Only the two patient-keyed FKs are `DEFERRABLE INITIALLY DEFERRED` (the patient-merge sweep re-points `patient_uid` under `SET CONSTRAINTS ALL DEFERRED`). No relation fields are added to `schema.prisma` for the new FKs (`check:prisma-relations` budget); the mirror carries scalars, uniques and indexes only.

None of the six new tables (§4.1–§4.6) is baseline-owned. Of the tables `NNN` alters, `dialysis_sessions`, `ot_schedules`, `surgical_implants` and `clinical_ai_biomed_devices` **are** baseline-owned: every change to them is `ALTER TABLE … ADD COLUMN` / `ADD CONSTRAINT` / `CREATE UNIQUE INDEX`, never an inline re-declaration, so the census manifest and its `expectedAbsentCount` (411) do not change. `dialyzer_reuse_register`, `instrument_sets`, `sterilization_loads` and `set_issue_log` are not baseline-owned and are altered the same way. `dialysis_patients` and `patient_bloodborne_markers` are **not altered** by this lane (§3.3, §4.7, §4.10).

## 5. Flows

### 5.1 Dialysis

**Capture** — `POST /api/v1/dialysis/sessions/:id/dialyser`, idempotency scope `dialysis_dialyser_capture`, session guard before the claim. Body `{ manufacturer_serial?, device_tag?, model_name?, manufacturer?, hospital_asset_id?, baseline_tcv_ml?, initial_cycle_count?, exposure_acknowledgement?: { reason } }` — exactly one of `manufacturer_serial` / `device_tag`. Inside one tenant transaction, session locked `FOR UPDATE`:

1. Session status ∈ {`scheduled`, `in_progress`}, no open usage on the session → else 409 `DIALYSER_ALREADY_CAPTURED`. The `dialyser` category policy must be reprocessable → else 409 `RPD_POLICY_NOT_REPROCESSABLE` (dark by default: the capture route refuses until a policy exists, and the legacy free-text `dialyser` column keeps working as today).
2. Resolve the device `FOR UPDATE` by tag, or by `(tenant, 'dialysis', manufacturer_serial)`; a serial nobody has seen mints a row (`enrolled_via = 'session_capture'`, `status = 'available'`, `cycle_count = initial_cycle_count ?? 0` with `metadata.enrolled_mid_life = true` when non-zero, `max_cycles_snapshot` from policy) and a link row dedicated to the session's patient with `baseline_tcv_ml` if given. A tag unknown in the tenant → 404 `RPD_DEVICE_NOT_FOUND`; a tag whose device is not `dialysis` → 409 `RPD_DOMAIN_MISMATCH`.
3. **Dedication**: link row exists and `dedicated_patient_uid <> session patient` → 409 `DIALYSER_DEDICATED_TO_ANOTHER_PATIENT`. No override exists for this; a dedicated dialyser on another patient is a never event.
4. Device status must be `available` → else 409 `RPD_DEVICE_NOT_AVAILABLE` with the status. At the cycle ceiling (`cycle_count = max_cycles_snapshot`) → 409 `RPD_MAX_CYCLES_REACHED`.
5. The resolver's live `Decision` (§3.3; **DEPENDS ON Phase 1**) is frozen as `reuse_screen` — the evidence snapshot of what the capturing user saw, never re-read for a later decision. The device's own `exposure_flag` under rule `discard` blocks capture (`RPD_EXPOSURE_BLOCKED`) **unless the device is dedicated to this same patient** — the exposure is that patient's own history, and refusing a dialyser to the patient it was exposed by protects nobody; the capture records `metadata.exposure_same_patient = true`. Under `override_allowed` on a flagged device the acknowledgement reason is required (`RPD_ACKNOWLEDGEMENT_REQUIRED`) and a safety review is written (§5.4).
6. Write the usage row (`dialysis_session_id`, `patient_uid`, `reuse_cycle = device.cycle_count`, `capture_source`), device → `in_case`, `dialysis_sessions.dialyser = COALESCE(model_name, manufacturer_serial)` and `reuse_count = reuse_cycle` (the legacy columns become derived, so the today board and the completion billing path keep working unchanged). Audit `rpd.device.captured`; realtime `dialyser-captured`.

**Isolation warnings** at `startSession` / `scheduleSession` / `PATCH /sessions/:id/machine` per §3.4 — a live `Decision` each time (DEPENDS ON Phase 1).

**Reprocessing record** — `POST /api/v1/dialysis/sessions/:id/reuse-register` (existing route; now claims a key: scope `dialysis_reuse_register`, `retainOnServerError: true` because a per-session upsert has no self-blocking `from` list — scouting risk 8). Body: 418's fields plus `measured_tcv_ml`, `reprocessing_agent`, `disinfectant_contact_minutes`, `disinfectant_concentration_pct`, `acknowledgement?: { reason }`. Behaviour:

- **No policy for `dialyser`** → the legacy path, byte for byte (free-text serial, typed count, upsert). The feature is dark.
- **Policy on, session has an open usage** → the device is the usage's device; `reuse_cycle_count` in the body must equal `usage.reuse_cycle` or be absent → else 409 `DIALYZER_REUSE_CYCLE_DERIVED` (behaviour change; the admin modal renders the count read-only).
- **Policy on, no usage, `dialyzer_serial` present** → implicit capture (steps 2–6 above with `capture_source = 'system'` and no acknowledgement path: an implicit capture on a restricted patient refuses with the capture code rather than guessing), then continue.
- Disposition is decided by `computeDispositionOptions` (§5.3) over a **fresh `Decision`** re-resolved inside the transaction — the frozen `reuse_screen` is not consulted, so a marker recorded since capture reaches this decision (§3.3); the `Decision` acted on is then frozen as `post_use_screen`. Body `status = 'in_use'` asks for `reprocess`; `discarded` asks for `discard`; `quarantined` asks for `quarantine`. A request outside the allowed set → 409 `RPD_DISPOSITION_NOT_ALLOWED` carrying `allowed`, `discard_reason` and `blocked_code`. `reprocess` under `unknown + warn` or `restricted + override_allowed` requires `acknowledgement.reason`.
- `reprocess`: device `return` (→ `awaiting_reprocessing`), then the integrity verdict: `integrity_test_result = 'pass'` **and** TCV within threshold (`measured_tcv_ml >= baseline_tcv_ml × tcv_min_pct / 100`, evaluated only when both are known; a missing baseline records `tcv_pct_of_baseline = NULL` and passes) → `reprocessed` (`cycle_count + 1`, `last_cycle_type = 'chemical'`, `last_function_check = 'pass'`, → `available`), usage `sent_for_reprocessing`; TCV below → device `discard` reason `tcv_below_threshold`, usage `discarded_tcv_below_threshold`, register `status = 'discarded'`; `integrity_test_result = 'fail'` → device `discard` reason `integrity_test_failed`, usage `discarded_integrity_failed`.
- `discard` / `quarantine`: device `discard` (reason from the screen or `other`) / `quarantine` (reason `bloodborne_exposure`), usage disposition accordingly; `exposure_markers` derived from `Decision.isolation_class` (§3.3 — a single class names its marker; `isolation_mixed` sets the flag alone).
- The 418 row is upserted as today with `device_id`, `device_usage_id`, `reuse_cycle_count = usage.reuse_cycle`, `session_reuse_count = usage.reuse_cycle`, the TCV and agent fields; **a second write for a session whose usage is already returned** answers the stored row with 409 `DIALYZER_REUSE_REGISTER_SETTLED` unless the body is identical (notes may still be edited — `notes` is the one column a settled row accepts). Audit `dialysis.reuse_register.recorded`; realtime `reuse-register-updated`.

**Read** — `GET /api/v1/dialysis/sessions/:id/dialyser` returns `{ usage, device, link: { dedicated_patient_uid, baseline_tcv_ml }, reuse_restriction (the live Decision, projected), allowed_dispositions, isolation: { codes, isolation_warnings, warn_only, enforcement_enabled, override } }` or `{ usage: null, … }` when nothing is captured. `isolation` is not projected because it carries no class (§3.4 interim payload, §3.5): this read does **not** pass `includeIsolationClass`, so its `Decision` has no class to publish and the warnings are read back from the session row. DEPENDS ON Phase 1. The existing `GET /sessions/:id/reuse-register` is unchanged in shape and gains the new columns.

**Cancel** — `POST /api/v1/dialysis/sessions/:id/cancel` (existing route, existing guard). `cancelSession` moves from the bare client into `setTenantTx` with the session locked `FOR UPDATE`; after the status walk is checked and **before** the status `UPDATE`, `dialysisReuseService.onSessionCancelledTx(tx, { session, target, context })` runs:

1. No usage row for the session → nothing (nothing was captured, or the feature is dark). The cancel proceeds as today.
2. The session's usage is already closed (`returned_at` set), **or** a `dialyzer_reuse_register` row references `device_usage_id = usage.id` → 409 `RPD_USAGE_NOT_CANCELLABLE`. Use was recorded on this session: the statutory row says the dialyser was used here, and `cancelled` would contradict it. Such a session ends by `complete`, not `cancel`.
3. The session is `in_progress` (`actual_start_at` set) → 409 `RPD_RETURN_REQUIRED`. Blood contact happened or cannot be ruled out; the reprocessing record must be written first (which closes the usage and lands the device in `available`, `quarantined` or `discarded` by the rule) — and once it is written, rule 2 applies. Patient-contact uncertainty means reprocess, never release. The usage table carries no contact-time column — 418's `disinfectant_contact_minutes` is a reprocessing-time field, not patient contact — so the owner's state is the contact signal.
4. Only a `scheduled` session (`→ cancelled` or `→ no_show`) un-captures: `reprocessableDeviceService.uncaptureDeviceTx` closes the usage (`post_use_disposition = 'cancelled_before_use'`, `returned_at = now()`, `returned_by = actor`, `metadata.cancel_target`), applies `uncapture` (device `in_case → available`, `current_usage_id` cleared, `cycle_count` unchanged, no reprocessing field written), audits `rpd.device.uncaptured`, and nulls `dialysis_sessions.reuse_count` (it claimed a cycle that never ran; the `dialyser` text is left — nothing reads it on a cancelled session).

Every refusal runs before the cancel writes anything, and a refused un-capture fails the cancel — there is no best-effort branch here, because a cancel that succeeds while the device stays `in_case` is the defect this closes. The released dialyser is captured again on the patient's next session at the same `reuse_cycle` (§4.4).

**Machines** — `GET /api/v1/dialysis/machines`, `POST /machines`, `PATCH /machines/:id` (scope `dialysis_machine`), roles `DIALYSIS_MACHINE_ADMIN_ROUTE_ROLES` = `DIALYSIS_ROUTE_ROLES ∩ {NURSING_INCHARGE, IP_INCHARGE, ICU_INCHARGE, ADMIN, SUPER_ADMIN}` (an intersection, so the gate can never be dead). `PATCH /sessions/:id/machine` `{ machine_no, isolation_override_reason? }` re-evaluates §3.4 and is on the session guard.

### 5.2 OT (four hooks inside `cssdService`'s transactions; dark without a policy)

- **`issueSet`** (`cssdService.js:731`): after the set is locked and the existing refusals have run, `cssdReuseHooks.onSetIssuedTx(tx, { set, issue, otSchedule, context })`: policy for `set.set_type` reprocessable → resolve or mint the set's register row (`enrolled_via = 'set_issue'`, `hospital_asset_id = set.barcode`, `status = 'available'`, `cycle_count = 0` with `metadata.enrolled_from_existing_set = true`); device must be `available` (a set that is `quarantined` in the register refuses issue with 409 `CSSD_SET_QUARANTINED` naming the reason); device `exposure_flag` under `discard` or `quarantine` → 409 `CSSD_SET_EXPOSURE_BLOCKED`, under `override_allowed` → `acknowledgement.reason` required (`CSSD_SET_ACKNOWLEDGEMENT_REQUIRED`); serology screen for `ot_schedules.patient_uid` → `reuse_screen`; usage row (`ot_schedule_id`, `set_issue_log_id`, `patient_uid`, `reuse_cycle`, `capture_source = 'cssd_issue'`); device `capture` → `in_case`. `POST /api/v1/cssd/issues` now claims a key (scope `cssd_set_issue`; the admin `createCssdIssue` caller moves to `core.ts` with a key).
- **`transitionIssue` → `returned`**: `onSetReturnedTx`: post-use screen; `computeDispositionOptions` for the OT domain — there is no operator disposition at return, the rule decides: `clear` → device `return` (→ `awaiting_reprocessing`), usage `sent_for_reprocessing`; `restricted` under `quarantine` → device `return` then `quarantine` (reason `bloodborne_exposure`, flag + markers), usage `quarantined_bloodborne_exposure`; under `discard` → device `return` then `discard` (reason `bloodborne_exposure`) and `instrument_sets` set `usable = false, requires_reprocessing = true` (its status stays `returned`; the board still shows it); under `override_allowed` → `return` with the flag stamped and no acknowledgement (nobody is choosing anything at return — the acknowledgement was taken at issue); `unknown` under `warn` → `return`; under `block_return` → `return` then `quarantine` (reason `serology_required`) since a set cannot be left in theatre. `return_condition = 'contaminated'` additionally stamps `metadata.return_condition` on the usage.
- **`transitionIssue` → `cancelled`** (`:908`; reachable only from `issued` — `ISSUE_TRANSITIONS.in_theatre` does not admit it, `cssdService.js:29-31`): `onIssueCancelledTx(tx, { issue, patch, context })` runs after the transition check and **before** the shared `set_issue_log` UPDATE. No register row for the set, or no usage for this issue → nothing (dark, or issued before a policy existed). The usage already closed → 409 `RPD_USAGE_NOT_CANCELLABLE` — unreachable through today's `ISSUE_TRANSITIONS`, kept so a later widening of that table cannot silently release a used set. `issue.theatre_use_started_at` set, **or** the cancel body declares `pack_opened: true` → 409 `RPD_RETURN_REQUIRED`: a pack opened at the trolley may have touched the field, so it is returned (`return_condition` as found) and the return rule decides — patient-contact uncertainty means reprocess. Otherwise `uncaptureDeviceTx`: usage `cancelled_before_use`, device `in_case → available`, cycle unchanged, `rpd.device.uncaptured`; the existing cancel branch then restores `instrument_sets` to `available` / `sterilized` exactly as today, and the next `issueSet` of the same set captures at the same `reuse_cycle` (the cycle unique is partial on `cancelled_before_use`, §4.4). A refused un-capture fails the cancel.
- **`transitionSterilizationLoad`** (`:588`): `onLoadTransitionedTx(tx, { load, status, setIds })`: for every set in `set_ids` with a register row: `passed` → if `load.cycle_type ∈ policy.allowed_cycle_types` and the device is `awaiting_reprocessing` or `in_cssd`, `reprocessed` (`cycle_count + 1`, `last_cycle_type = load.cycle_type`, `last_sterilization_load_id = load.id`, `last_function_check = 'not_required'`, → `available`) and the most recent returned usage's `sterilization_load_id = load.id`; a cycle type the policy forbids → `quarantine` with reason `cycle_type_not_allowed:<type>` and a warning in the load result's new `affected_devices[]`; a device already `quarantined` (exposure) is left quarantined — a passed load does not clear an exposure hold; `failed` → `quarantine` reason `sterilization_failed` for devices `awaiting_reprocessing` / `in_cssd`; devices `in_case` are untouched (the load never had them). **A `sterilization_failed` quarantine is not cleared by a later passed load either** — the same "a passed load never clears a hold" rule, deliberately not special-cased: after a failed load CSSD `release`s the device (→ `awaiting_reprocessing`) and runs it again, and the release is the human acknowledgement that the failed load was looked at. One extra click per failed load per device is the friction this buys; a unit that finds it too much argues with the rule, not around it. At the cycle ceiling a `passed` load discards (`max_cycles_reached`) instead of releasing — "maximum-cycle discard happens on release without a click" (cath spec §14).
- **CSSD `discard` on an OT device** also sets `instrument_sets.status = 'retired'`, `retired_at`, `retired_by`, `retirement_reason` (the register's `discard_note` or reason) — the one place the register writes the set's status.

What this lane does **not** add for OT (recorded, not hidden): a failed load still does not recall sets already issued to a patient, and there is no BI-to-patient lookback (§10); there is no single-use flag on any OT item; the WHO sign-in strip is a Staff surface in §7.2 reading the same `reuse_restriction`, not a gate.

### 5.3 Shared disposition rule

`reprocessableDeviceRules.computeDispositionOptions({ domain, usage, policy, settings, restriction, device })` is `cathDeviceReuseService.computePostUseOptions` with the implant clause removed (no OT or dialysis category is an implant), `units_max` fixed at 1, and one added branch: `restricted` (or the device's own `exposure_flag`) under `reactive_patient_rule = 'quarantine'` → `{ dispositions: ['quarantine', 'discard'], quarantine_reason: 'bloodborne_exposure', reason_codes: ['bloodborne_restricted_quarantine'] }`. The evaluation order is 765's as built: the device's own flag, then the ceiling, then the patient's screen. Adjacent: the reviewed correction command for a wrong legacy `'positive'` that review round 1 asked for is the same command's other direction.
10. **D11 — may a routing role learn *which* marker isolates a patient, or only *that* one does?** (§2, and §3.4's interim payload.) **YES** costs nothing: `isolation_warnings` regains `required_class` and the design is what review round 1 settled on. **NO** costs one column swap and one settings block: `dialysis_machines.isolation_group` (a tenant-defined label such as "Bay 1") replaces `isolation_class` as the routing key, the class → group mapping sits in this lane's per-tenant isolation settings under infection-control / admin edit only, `evaluateIsolationForSessionTx` maps class → group server-side, and the warning, the mismatch codes, the audit metadata and the device's `exposure_markers` all stop naming a marker. **The §3.3 resolver contract is identical under either branch** — Phase 1 is not blocked by this question, and neither is any other task. Until it is answered the interim shape of §3.4 ships: routing uses the class server-side through the opt-in flag and nothing user-facing carries it. This supersedes review round 1's Fix-6 (§3.5); it is a narrower question than D10, and a YES to D10 moots it only for the three roles D10 admits. **One limit the owner should price honestly (dev-ea):** under the NO branch the class-to-group mapping is opaque in the *data*, not in the *world* - a technician who sees which patients route to "Bay 1" learns the cohort within a week, and "Bay 1 is the hep B bay" becomes ward knowledge whatever the payload says. That is an inference risk, not a disclosure, and it does not argue against the design (routing has to happen somewhere physical), but `isolation_group` *reduces the blast radius* - no marker in an API response, a log line or an export - without *eliminating the knowledge*. The owner should choose it for the former and not believe it achieves the latter.

Settled since round 1 (not an owner decision, recorded so the history is legible): `isolation_class` on the `Decision` is **agreed with dev-ea as an opt-in field** behind `includeIsolationClass` (§3.3), not the unconditional fifth field Plan 4 first asked for. dev-ea rejected that on the ground that a value of `'hiv'` is serology whatever the caller calls it — the "routing instruction" reframing is what produced two earlier disclosures — and the opt-in shape is the counter-proposal both lanes accepted.
